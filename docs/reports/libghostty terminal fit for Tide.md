# Keep SwiftTerm Now, Prove libghostty-vt Later

libghostty is the umbrella name for Ghostty's embeddable terminal libraries, and in October 2026 only one of them is offered to outside developers: **libghostty-vt**, an MIT-licensed C library over a Zig core that parses terminal output, keeps screen and scrollback state, encodes keys, mouse and paste, and hands a host-written renderer a dirty-tracked view of the screen, but ships no renderer, font stack or PTY. The library most people picture, Ghostty's full embedder API with its Metal renderer (GhosttyKit), is documented as internal to the macOS app, **lost its iOS build on August 12, 2026**, and cannot accept bytes from an SSH channel without a patch. The engine is mature and the API is not: libghostty-vt is untagged (`0.1.0-dev`), warns that breaking changes are expected, renames or removes symbols every few months and missed its own target of a tagged release by March 2026, and upstream builds it nightly for iPhone and iPad but verifies iOS only by compiling it. Adoption is real all the same. **Termius moved its iOS terminal to libghostty in version 8.0.3 on October 14, 2026**, joining rootshell, VVTerm and Echo on the App Store, yet every iOS app whose Ghostty integration could be inspected runs a patched build of the full library, so the route upstream supports has no shipping iPad precedent and the route iPad apps ship has no upstream support. None of this changes Tide's architecture: iOS still forbids local shells, so the terminal is an SSH client fed by Citadel, and over SSH users feel frame pacing, main-thread stalls and input latency, which nobody has measured for either engine on an iPad. Tide should keep SwiftTerm and move to its 2.0 line, put a small `TerminalEngine` protocol between Citadel and the terminal view before SSH lands, spike libghostty-vt with a Tide-owned Core Text renderer behind it, and switch only when on-device measurements, input parity and API stability all pass a gate; the patched full library is worth a day as a yardstick and never as the shipping engine. The deciding cost is not the Zig build, which a signed prebuilt framework removes, but a second custom text-input and rendering surface beside the editor engine Tide already plans to own.

## libghostty is two libraries, and outsiders get only the VT core

Ghostty's README describes libghostty as "a cross-platform, zero-dependency C and Zig library for building terminal emulators or utilizing terminal functionality (such as style parsing)" ([Ghostty README](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/README.md#L31-L37)) and says the project is "breaking libghostty down into separate libraries, starting with `libghostty-vt`" ([Ghostty README](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/README.md#L151-L155)). Two products exist in October 2026, and the source tree draws a hard line between them. The full embedder header, `ghostty.h`, opens by calling itself "Ghostty's internal embedder API, a.k.a. 'libghostty-internal'", states that "The only consumer of this API is the macOS app", and tells "External embedders" to "instead use `libghostty-vt`" ([ghostty.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty.h#L1-L11)). **libghostty-vt is therefore the only libghostty library meant for anyone else.** Its umbrella header calls it "a C library which implements a modern terminal emulator, extracted from the Ghostty terminal emulator" that handles "parsing terminal escape sequences, maintaining terminal state, encoding input events" along with "scrollback, line wrapping, reflow on resize, and more" ([vt.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt.h)). About 30 sub-headers add an incremental render state, a formatter that emits plain text, VT or HTML, binary snapshots, scrollback search, OSC and SGR parsers, paste safety, selection, Unicode width tables, Kitty graphics state, custom allocators, and key, mouse and focus encoders ([include/ghostty/vt](https://github.com/ghostty-org/ghostty/tree/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt)).

What libghostty-vt leaves out defines an embedder's work. **It ships no renderer, no font stack and no PTY.** The render state is "Render state for creating high performance renderers", a viewport with dirty tracking for a renderer the host writes ([render.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/render.h)); fonts appear nowhere in the terminal API, and the Unicode header offers only the width tables "the terminal itself uses" ([unicode.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/unicode.h)); the library "does not create a timer or background thread" ([terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)); and Kitty images decode only after the host installs a PNG decoder through a system callback ([sys.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/sys.h)). Upstream's reference app makes the division of labor concrete. Ghostling is a single C file of 1,618 lines on Raylib, "single-threaded (although libghostty-vt supports threading)", with a 2D renderer and "no shaping or layout", and its README files tabs, splits, configuration and the search UI under "things that libghostty consumers are expected to implement on their own" ([Ghostling](https://github.com/ghostty-org/ghostling)).

The full library is the one people picture when they hear "Ghostty on iOS": configuration, font discovery and shaping, the Metal renderer, keybindings, splits and an inspector, behind a surface that draws itself into an `NSView` or `UIView` ([ghostty.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty.h#L1139-L1281)). It handles input methods itself, with `ghostty_surface_preedit` for marked text and `ghostty_surface_ime_point` for the candidate window ([ghostty.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty.h#L1198-L1221)). What it cannot do is listen to SSH. **A full-library surface always spawns a local command**: its configuration struct carries `command`, `working_directory` and `env_vars` but no host-supplied byte stream ([ghostty.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty.h#L489-L521)), and the only upstream I/O backend, `Exec.zig`, starts a process ([src/termio](https://github.com/ghostty-org/ghostty/tree/main/src/termio)). Every iOS app that wants Ghostty's renderer has to patch in a backend of its own.

| | libghostty-vt | Full libghostty (GhosttyKit, `ghostty.h`) |
|---|---|---|
| Upstream status | Supported for outside embedders, with a Doxygen reference and 30+ examples | "Internal embedder API" whose "only consumer" is the macOS app; mostly undocumented |
| Scope | Parser, terminal state, scrollback and reflow, render state, key, mouse, focus and paste encoders, selection, search, snapshots, Kitty graphics state, formatter | All of that plus process I/O, configuration, fonts and shaping, the Metal renderer, keybindings, splits and an inspector |
| Rendering and fonts | None; the host writes them | Ghostty's own, drawn into an `NSView` or `UIView` |
| Bytes from an SSH channel | `ghostty_terminal_vt_write` | No API; surfaces spawn a local command |
| Input methods | The host's job, with width helpers for preedit text | `ghostty_surface_preedit` and `ghostty_surface_ime_point` |
| iOS builds upstream | Device and arm64 simulator, as a nightly signed xcframework | Removed on August 12, 2026; macOS only |
| Swift packaging | Upstream xcframework and `import GhosttyVt`; no Swift wrapper in the community index | Community forks and packages only (libghostty-spm, Termini, remux) |
| iOS device code size (`__TEXT`, measured) | 1.86 MB | 9.67 MB |

Sources: [ghostty.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty.h), [vt.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt.h), [libghostty Doxygen](https://libghostty.tip.ghostty.org/), [examples](https://github.com/ghostty-org/ghostty/tree/48dde97e0413a27064e4c6182db3df6ee999db7d/example), [Config.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/Config.zig#L134-L137), [GhosttyXCFramework.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/GhosttyXCFramework.zig), [awesome-libghostty](https://github.com/Uzaaft/awesome-libghostty); sizes measured with `xcrun size` on the public [tip release](https://github.com/ghostty-org/ghostty/releases/tag/tip) and [libghostty-spm release](https://github.com/Lakr233/libghostty-spm/releases/tag/upstream.1e9e14af5df1-3) archives, before dead-stripping.

For an SSH client the libghostty-vt contract is short. The host pushes received bytes in with `ghostty_terminal_vt_write` and hears back through callbacks registered with `ghostty_terminal_set`: `WRITE_PTY` returns the terminal's answers to queries and mode reports, and other effects report the bell, title, working directory (OSC 7), clipboard reads and writes (OSC 52), desktop notifications, progress, OSC 133 semantic prompts, OSC 7501 program status and synchronized-output holds. "All callbacks are invoked synchronously during VT writes", must not re-enter `vt_write` and must not block ([terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)). Rendering pulls rows and cells through iterators with global and per-row dirty flags, and because the update "only needs read/write access to the terminal instance during the update call", a renderer can lock, begin the update, unlock and finish while the I/O thread keeps writing ([render.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/render.h)). Input runs the other way through encoders. Keys are physical, layout-independent codes "based on the W3C UI Events KeyboardEvent code" plus UTF-8 text, with all five Kitty keyboard flags, and mouse, focus and paste have encoders of their own ([key/event.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/key/event.h), [key/encoder.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/key/encoder.h), [mouse/encoder.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/mouse/encoder.h)). Swift reaches all of it through the xcframework's bundled module map with `import GhosttyVt`, filling in the `size` field of each option struct itself ([Swift example](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/example/swift-vt-xcframework/Sources/main.swift)).

## The engine is proven; the API, the tag and the roadmap are not

The case for libghostty-vt is that its code is not new. The README calls the functionality "extremely stable (since its been proven in Ghostty GUI for a long time)" while warning that "the API signatures are still in flux" ([Ghostty README](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/README.md#L157-L160)), and the September 2025 announcement promised the GUI's "SIMD-optimized parsing, very good Unicode support, highly optimized memory usage, a robust fuzzed and Valgrind-tested codebase", Kitty graphics and tmux control mode, with no dependencies, "not even libc" ([Libghostty Is Coming](https://mitchellh.com/writing/libghostty-is-coming)). A fuzz corpus lives in the repository ([test/fuzz-libghostty](https://github.com/ghostty-org/ghostty/tree/main/test/fuzz-libghostty)), the library already builds for more platforms than the GUI, including Android, Windows and WebAssembly ([GhosttyLibVt.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/GhosttyLibVt.zig)), and Ghostty itself has 62,451 GitHub stars ([ghostty-org/ghostty](https://github.com/ghostty-org/ghostty)). Its speed claim is deliberately modest: Ghostty "aims to be in the same class as the fastest terminal emulators. In some benchmarks it is faster, in others it is slower" ([About Ghostty](https://ghostty.org/docs/about)).

The API tells a different story. The umbrella header warns that this "is an incomplete, work-in-progress API. It is not yet stable and is definitely going to change" ([vt.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt.h)), the build declares `0.1.0-dev` ([build.zig](https://github.com/ghostty-org/ghostty/blob/main/build.zig)), and the README says "We haven't tagged libghostty with a version yet" ([Ghostty README](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/README.md#L168-L170)). **Sixty-nine commits touched `terminal.h` alone between April 6 and October 21, 2026** ([terminal.h history](https://github.com/ghostty-org/ghostty/commits/main/include/ghostty/vt/terminal.h)), and commits to libghostty-vt's headers ran 26, 28, 4, 22, 44, 12 and 27 a month from April through October 21 ([header history](https://github.com/ghostty-org/ghostty/commits/main/include/ghostty)). Several broke callers. The terminal constructor took an options struct in April and now takes positional allocator, output, column and row arguments ([PR #12149](https://github.com/ghostty-org/ghostty/pull/12149), [terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)); `ghostty_kitty_image_get` was renamed in April; mode getters and setters and the snapshot BLAKE3 digests were removed in August; and an OSC "context signal" was renamed on October 14 ([header history](https://github.com/ghostty-org/ghostty/commits/main/include/ghostty)). The counterweight is visible care for a future stable ABI: caller-sized option structs, enums padded to a maximum value, a dylib export check limited to `_ghostty_` symbols, a CMake soname tied to the major version and a `-Dvt-features` switch "to compile out unused features" ([build_info.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/build_info.h), [check script](https://github.com/ghostty-org/ghostty/blob/main/.github/scripts/check-apple-libghostty-vt.nu), [CMakeLists.txt](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/CMakeLists.txt), [PR #13834](https://github.com/ghostty-org/ghostty/pull/13834)). The conventions show where the API is heading, and the commit log shows what each upgrade costs until it arrives: by this report's estimate, hours of adapter edits per bump, provided every C call sits inside one Swift module and Tide pins an exact commit.

The roadmap has already slipped once. In September 2025 Mitchell Hashimoto called the release a "public alpha (not promising API stability)" and wrote "I hope to ship a tagged version of libghostty-vt within the next 6 months" ([Libghostty Is Coming](https://mitchellh.com/writing/libghostty-is-coming)). The 1.3.0 release notes in March 2026 reported that libghostty "was successfully extracted and is now available as a standalone Zig module", split the GUI and library release cycles and conceded "We aren't sure yet when we'll tag the first libghostty releases" ([Ghostty 1.3.0 release notes](https://ghostty.org/docs/install/release-notes/1-3-0)); on October 21 the tag still did not exist, about seven months past the hoped-for date. The longer plan, a family of `libghostty-<x>` libraries for "GPU rendering (provide us with an OpenGL or Metal surface and we'll take care of the rest), GTK widgets and Swift frameworks that handle the entire terminal view", carries no dates ([Libghostty Is Coming](https://mitchellh.com/writing/libghostty-is-coming)). **Tide cannot plan around an official Swift terminal view or Metal renderer.** What is growing quickly is libghostty-vt itself, and much of the growth answers embedders: binary snapshots began as a request for "lossless state transfer" ([discussion #11998](https://github.com/ghostty-org/ghostty/discussions/11998)), Kitty image data reached the render state after an embedder issue ([#12111](https://github.com/ghostty-org/ghostty/issues/12111)), virtual Kitty placements are under discussion ([discussion #14698](https://github.com/ghostty-org/ghostty/discussions/14698)), and Mitchell's October 2026 OSC 7501 program-status protocol arrived as a libghostty-vt callback ([mitchellh.com](https://mitchellh.com/writing), [terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)). On October 21 a merged PR moved the desktop app's own Kitty placements onto the render state ([PR #14789](https://github.com/ghostty-org/ghostty/pull/14789)), which suggests the GUI is converging on the same render path embedders use; that is an inference from the PR, not a stated plan, but it makes the render-state API the most durable part of the library.

Ownership risk is low, and concentrated. Ghostty is MIT-licensed and since December 3, 2025 has been fiscally sponsored by Hack Club, a 501(c)(3), under a structure in which "the project cannot be sold off or repurposed for commercial gain" ([Ghostty Is Now Non-Profit](https://mitchellh.com/writing/ghostty-non-profit)). Mitchell's July 2026 post on his new company says the project has "about a dozen core maintainers", that Superlogical "will consume the same MIT-licensed components available to everyone else", and that Ghostty's "mission, governance, license, technical goals, and roadmap do not change" ([Superlogical](https://mitchellh.com/writing/superlogical)). The API itself has a bus factor close to one: **Mitchell authored 134 of the 163 commits that touched libghostty-vt's headers between April 1 and October 21, 2026** ([header history](https://github.com/ghostty-org/ghostty/commits/main/include/ghostty)), and the code owners file limits macOS maintainers to libghostty work "insofar as it impacts the macOS apprt" ([CODEOWNERS](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/CODEOWNERS#L74-L135)). Two process facts matter to an iOS embedder. Non-maintainers cannot open issues, so an iOS use-after-free report was closed in June by a bot that asks for "a discussion first" ([#13021](https://github.com/ghostty-org/ghostty/issues/13021)). And Ghostty announced in April 2026 that it "will be leaving GitHub", promising a read-only mirror; it was still merging there on October 21, but Mitchell's Go bindings already name another forge as their "Source of truth" ([Ghostty Is Leaving GitHub](https://mitchellh.com/writing/ghostty-leaving-github), [PR #14793](https://github.com/ghostty-org/ghostty/pull/14793), [go-libghostty](https://github.com/mitchellh/go-libghostty)). Package URLs and bug-report paths could move under Tide within months.

## Upstream compiles libghostty-vt for iPad, but every inspectable iPad app runs a fork

### The supported route is a signed nightly framework, tested only by compiling

The build system states upstream's iOS policy in two places: a full iOS build fails with "only libghostty-vt supports iOS (-Demit-lib-vt)", and "lib-vt is the only thing we still build for iOS", with a minimum of iOS 13 ([Config.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/Config.zig#L134-L137), [Config.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/Config.zig#L810-L815)). The xcframework carries macOS universal, iOS device and iOS simulator slices; the simulator slice is arm64-only with an explicit `apple_a17` CPU model, and tvOS, watchOS and visionOS wait on Zig's standard library ([GhosttyLibVt.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/GhosttyLibVt.zig#L125-L215)). Since April 2026 CI has published the framework on the rolling `tip` release, and "Users can also drag and drop the XCFramework directly into Xcode" ([PR #12149](https://github.com/ghostty-org/ghostty/pull/12149)). **On October 21, 2026 the `tip` release carried a 15,120,677-byte `ghostty-vt.xcframework.zip` with a minisign signature, rebuilt at 03:21 UTC that day, and no versioned release exists** ([tip release](https://github.com/ghostty-org/ghostty/releases/tag/tip)). That removes the obstacle most often cited against libghostty on iOS, because a project consuming libghostty-vt never has to run Zig. Building from source does require Zig 0.17.0 and a macOS host with the Apple SDK ([build.zig.zon](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/build.zig.zon#L6), [test.yml](https://github.com/ghostty-org/ghostty/blob/main/.github/workflows/test.yml)), and that minimum is still moving: libghostty-spm's README gives 0.16.0 as the minimum for its October 19 pin, and upstream patched Zig's process replacement for iOS on October 20 ([libghostty-spm](https://github.com/Lakr233/libghostty-spm), [commit 84c100fe1](https://github.com/ghostty-org/ghostty/commit/84c100fe1)). Upstream fixed the main App Store trap in July: "Zig's Mach-O linker does not emit LC_ENCRYPTION_INFO_64 for physical iOS dylibs", which "causes frameworks containing it to fail App Store validation", so Apple targets now link with Apple's linker and a CI script checks the encryption segment, install name and export list ([PR #13430](https://github.com/ghostty-org/ghostty/pull/13430), [check script](https://github.com/ghostty-org/ghostty/blob/main/.github/scripts/check-apple-libghostty-vt.nu)).

The support stops there, and upstream says so. The CI job builds and inspects the iOS slices on a macOS runner and never runs them ([test.yml](https://github.com/ghostty-org/ghostty/blob/main/.github/workflows/test.yml)), the official Swift example declares only `.macOS(.v13)` ([Package.swift](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/example/swift-vt-xcframework/Package.swift)), and the rationale given when the iOS app target was deleted was that "we verify iOS compatibility for `libghostty-vt` through compilation" ([PR #13759](https://github.com/ghostty-org/ghostty/pull/13759)). The research found no upstream iOS example or test app after August 2026. **Memory, threading, Metal integration and input on iPadOS are the embedder's problem.**

### The full library lost iOS on August 12, 2026

Two PRs merged on August 12, 2026 ended the full library's iOS life. PR #13759 deleted the iOS app with the line "Ghostty internal support for iOS is not important" ([PR #13759](https://github.com/ghostty-org/ghostty/pull/13759)), and PR #13760 stopped building the full xcframework for iOS, its author noting that this "will affect other awesome-libghostty projects" ([PR #13760](https://github.com/ghostty-org/ghostty/pull/13760)); GhosttyKit is now macOS-only ([GhosttyXCFramework.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/GhosttyXCFramework.zig)). In 2025 Mitchell had written that "iOS isn't an important target for us but I like to keep it working so that libghostty remains iOS compatible" ([#7643](https://github.com/ghostty-org/ghostty/issues/7643)). The deleted iOS view never solved input anyway: it was 84 lines, a `CAMetalLayer` with focus and size handling and no keyboard, IME or accessibility code ([SurfaceView_UIKit.swift](https://github.com/ghostty-org/ghostty/blob/9f9b8d1d0525e63106cfc0ea19775056b205ffb5/macos/Sources/Ghostty/Surface%20View/SurfaceView_UIKit.swift)). The one attempt to bring an iOS SSH path upstream, a "Manual termio backend" adding `ghostty_surface_write_output()`, was closed by its author the day it opened, with no maintainer comment ([PR #10484](https://github.com/ghostty-org/ghostty/pull/10484)), and the full library's app, I/O and reader threads carry an open deadlock in which "`ghostty_surface_free` deadlocks the app thread" ([#14245](https://github.com/ghostty-org/ghostty/issues/14245)).

### Every visible integration carries its own patch stack

That leaves forks. The most complete is **libghostty-spm** (MIT, 114 stars), which ships prebuilt GhosttyKit binaries for iOS 15 and later, Mac Catalyst and visionOS on top of **21 patches**: a host-managed I/O backend; iOS Metal fixes ("IOSurface +1px tolerance, synchronous present, 64-byte row alignment"); a lowered deployment target and a removed "private window blur API"; history replay with protocol responses suppressed; and custom shaders, the inspector and Sentry turned off ([libghostty-spm](https://github.com/Lakr233/libghostty-spm), [patches](https://github.com/Lakr233/libghostty-spm/tree/main/Patches/ghostty)). Its `GhosttyTerminal` product supplies the UIKit work upstream never did, about 110 Swift files including `UITextInput`, key commands and touch selection, around an `InMemoryTerminalSession` that takes host bytes through `receive(_:)` and returns input through a `write` closure ([UIKit sources](https://github.com/Lakr233/libghostty-spm/tree/main/Sources/GhosttyTerminal/Platform/UIKit), [InMemoryTerminalSession.swift](https://github.com/Lakr233/libghostty-spm/blob/main/Sources/GhosttyTerminal/InMemory/InMemoryTerminalSession.swift)). It also shows what a fork costs: weekly releases pinned to "upstream main's head of that Monday" and versioned `2.2.YYYYMMDDNN` (the latest, 2.2.2026101901, on October 19), withdrawn 1.4.0–1.4.13 and 1.5.0 tracks, and 248 commits from its owner against 18 from the next human contributor ([libghostty-spm](https://github.com/Lakr233/libghostty-spm), [releases](https://github.com/Lakr233/libghostty-spm/releases), [contributors](https://github.com/Lakr233/libghostty-spm/graphs/contributors)). The other projects follow the same pattern. VVTerm builds the `wiedymi/ghostty` fork at a pinned commit ([build.sh](https://github.com/vivy-company/vvterm/blob/main/scripts/build.sh)); Geistty depends on a `daiimus/ghostty` branch with an "External termio backend" and calls itself "essentially abandonware" ([Geistty](https://github.com/daiimus/geistty)); remux downloads a checksum-pinned GhosttyKit from its own fork's release ([fetch_ghosttykit.sh](https://github.com/h3nock/remux/blob/main/scripts/fetch_ghosttykit.sh)); and Termini downloads a prebuilt GhosttyKit and is "SSH-only" on iOS because "the sandbox blocks local `fork`/PTY" ([Termini](https://github.com/hudsonkit/Termini)). The only mobile project the research found that pairs libghostty-vt with a host-written renderer does so on Android: expo-libghostty uses a roughly 50 MB GhosttyKit on iOS and libghostty-vt with a Canvas renderer on Android ([expo-libghostty](https://github.com/arcboxlabs/expo-libghostty)).

### Termius proves demand, not a route

Adoption is real and recent. **Termius, an SSH client with 4.7 stars from 19,480 US ratings, shipped iOS 8.0.3 at 22:42 UTC on October 14, 2026 with "a new terminal rendering engine, powered by libghostty, that's faster, smoother, and more accurate"** ([App Store lookup](https://itunes.apple.com/lookup?id=549039908&country=us), [Termius changelog](https://docs.termius.com/changelog/ios)). Its changelog already lists an 8.0.6 dated October 23, two days after this research and not yet on the App Store, that fixes "terminal text selection when using a mouse", "input delay caused by shell integration (autocomplete)" and "RTL rendering issues in the terminal" ([Termius changelog](https://docs.termius.com/changelog/ios), [App Store lookup](https://itunes.apple.com/lookup?id=549039908)). Termius has published no engineering write-up, so whether it runs libghostty-vt under its own renderer or a patched full library is unknown, and that unknown matters: it decides whether a Tide-built renderer could reproduce Termius's gains. Smaller App Store apps have shipped on Ghostty all year, and headline claims need checking, as the table shows.

## Over SSH, frame pacing decides the contest, and nobody has measured it on iPad

SwiftTerm, Tide's current engine, is not standing still, and much of its 2026 work answers Ghostty directly. Version 1.12.0 in March added a "GPU backend, inspired by the Ghostty GPU engine on Apple platforms", OSC 8 links and the Kitty keyboard protocol ([v1.12.0](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.12.0)); its Metal path is opt-in through `setUseMetal(_:)` and rebuilds only dirty rows by default ([GPURendering.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/Sources/SwiftTerm/Documentation.docc/GPURendering.md)). Version 1.14.0 in July brought VoiceOver and public selection APIs to iOS, 1.16.0 added BiDi with Arabic shaping and 1.17.0 added OSC 133 ([v1.14.0](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.14.0), [v1.16.0](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.16.0), [v1.17.0](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.17.0)). After Tide's pin, 1.19.0 of August 18, came a 2.0 line: 1.99.0 on October 8 is "a major performance upgrade, but it came at the expense of changing some APIs", with new I/O, reworked Kitty graphics and XTGETTCAP ([v1.99.0](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.99.0)), and 1.99.1 on October 21 cut main-thread work ("fewer main-thread hops, a row cache by line, plain-cell glyphs, read coalescing") and added iOS pointer mouse reporting and OSC 7501 ([v1.99.1](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.99.1)). It renders Sixel, iTerm2 and Kitty images ([GraphicsSupport.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/Sources/SwiftTerm/Documentation.docc/GraphicsSupport.md)), uses test cases "extracted from xterm.js and Ghostty", and is "Fuzzed and abused" ([SwiftTerm README](https://github.com/migueldeicaza/SwiftTerm/blob/main/README.md)). It is no handicap in the market either: Secure ShellFish, built on it, drew the field's best sentiment in a sample of 353 recent App Store reviews averaging 4.80 ([ShellFish reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1336634154/sortby=mostrecent/json)). Its weak spots are iOS input bugs still open in October 2026: external keyboard shortcuts not activating, Option-as-Meta dropping Shift and double-tap ignoring mouse reporting ([#483](https://github.com/migueldeicaza/SwiftTerm/issues/483), [#591](https://github.com/migueldeicaza/SwiftTerm/issues/591), [#663](https://github.com/migueldeicaza/SwiftTerm/issues/663)).

Ghostty's advantages sit in the core and in the full library's renderer. libghostty-vt brings Kitty graphics with animation, tmux control mode and caller-driven scrollback compression ([src/terminal/kitty](https://github.com/ghostty-org/ghostty/tree/main/src/terminal/kitty), [build_info.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/build_info.h), [terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)), plus snapshots that restore complete terminal state "including any unfinished VT parser input" ([snapshot.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/snapshot.h)). Ligatures are on by default in Ghostty ("To disable programming ligatures, use -calt"), but they come from the full library's Core Text and HarfBuzz shapers, not from libghostty-vt ([config reference](https://ghostty.org/docs/config/reference), [src/font/shaper](https://github.com/ghostty-org/ghostty/tree/main/src/font/shaper)). The gaps are just as specific. Sixel came off Ghostty's to-do list ([#2772](https://github.com/ghostty-org/ghostty/issues/2772)), OSC 1337 serves the working directory and copy rather than inline images ([terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)), and **Ghostty has no BiDi support**: the "minimal RTL support" issue has been open since 2024 and several RTL pull requests closed unmerged ([#1442](https://github.com/ghostty-org/ghostty/issues/1442), [#13595](https://github.com/ghostty-org/ghostty/pull/13595), [#11079](https://github.com/ghostty-org/ghostty/pull/11079)), which makes the RTL fix in Termius's announced follow-up release unsurprising.

**Raw parsing speed will not decide this for Tide.** SwiftTerm's headless engine parses about 1,050 MiB/s on a light workload against a local PTY ceiling of about 290 MiB/s on one Mac ([PERFORMANCE.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/PERFORMANCE.md)), and an SSH channel to a remote host delivers far less than either. What users feel is frame pacing during full-screen TUI redraws, main-thread hitches while the SwiftUI workbench shares that thread, key-to-echo latency and emulation correctness; Blink's reviewers punished "corrupted screens even in simple stuff like top" ([Blink reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1594898306/sortby=mostrecent/json)). On the main thread there is concrete evidence. Profiling SwiftTerm's Metal renderer during a 10 Hz full-screen redraw found that "almost all of the renderer's main-thread time goes to rebuilding rows", with per-glyph `CTFontCopyPostScriptName` lookups at about 35% of rebuild time and uncached blank glyphs at about 20% ([#738](https://github.com/migueldeicaza/SwiftTerm/issues/738)), the cost 1.99.1's row cache attacks. Ghostty's full renderer runs off the main thread, and libghostty-vt's two-phase update lets a host renderer hold the terminal lock only briefly ([render.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/render.h)). That is the most plausible source of a real gain on a busy iPad workbench, and it remains an inference: Termius, rootshell ("ProMotion 120 Hz") and Geistty ("120fps") publish claims, not numbers, and no reproducible iOS benchmark of either engine exists ([Termius changelog](https://docs.termius.com/changelog/ios), [rootshell](https://github.com/kitknox/rootshell), [Geistty](https://github.com/daiimus/geistty)). Tide also does not yet turn on SwiftTerm's Metal path; no file in the app sources calls `setUseMetal` ([TerminalManager.swift](../../App/Sources/Model/TerminalManager.swift)), so the honest baseline for any comparison is SwiftTerm 2.x with Metal on, not today's default.

Size and memory favor libghostty-vt modestly. Measured with `xcrun size` on the public archives before dead-stripping, the libghostty-vt iOS device slice holds **1.86 MB of code** in 12 object files, 1.34 MB of it the Zig core and the rest vendored wuffs, compiler_rt and simdutf, while the full GhosttyKit slice from libghostty-spm holds 9.67 MB across 136 objects, including FreeType, libpng, zlib and Oniguruma ([tip release](https://github.com/ghostty-org/ghostty/releases/tag/tip), [libghostty-spm release](https://github.com/Lakr233/libghostty-spm/releases/tag/upstream.1e9e14af5df1-3)). SwiftTerm's compiled size was not measured. On memory, libghostty-vt gives the host scrollback caps in bytes or lines and an explicit compression call driven by the host's idle timer ([terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)), a useful knob on a platform whose per-app limits Apple does not publish and whose increased-memory entitlement is "only available on some device models" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit)). Neither engine's iOS footprint at large scrollback has been measured.

## A TerminalEngine seam lets Tide ship SwiftTerm now and switch on evidence

### Tide's terminal is an SSH client by necessity

Nothing in libghostty changes where Tide's shells run. "iOS can't spawn local shells -- no `fork`, no `exec`, no PTY," as Geistty's author puts it ([Geistty](https://github.com/daiimus/geistty)), and App Review Guideline 2.5.2 bars apps from downloading or executing code that changes their features ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Tide's README draws the same conclusion: "iOS apps cannot start processes, so full shells will come over SSH" ([Tide README](../../README.md)). Today a `TerminalSession` creates SwiftTerm's `TerminalView`, writes output with `feed(text:)` and routes keystrokes from the `send(source:data:)` delegate into a `LineEditor` and Tide's built-in `VirtualShell`; the delegate bridge leaves `sizeChanged` and `hostCurrentDirectoryUpdate` empty, and SwiftUI hosts the view through a `UIViewRepresentable` that returns it ([TerminalManager.swift](../../App/Sources/Model/TerminalManager.swift), [PanelView.swift](../../App/Sources/Views/Panel/PanelView.swift)). The project pins SwiftTerm `exactVersion: 1.19.0`, targets iOS 17 and compiles Swift 6 with `MainActor` as the default isolation ([project.yml](../../project.yml)). The planned transport is Citadel on SwiftNIO SSH, whose PTY sessions support `changeSize` for window changes alongside exec streams and SFTP ([Citadel TTY.swift](https://github.com/orlandos-nl/Citadel/blob/main/Sources/Citadel/TTY/Client/TTY.swift), [Citadel Client.swift](https://github.com/orlandos-nl/Citadel/blob/main/Sources/Citadel/Client.swift)). Citadel must close four gaps before 1.0 whatever the terminal: it signs RSA user authentication only as SHA-1 `ssh-rsa`, which OpenSSH 8.8 disables by default; it lacks keyboard-interactive authentication; it cannot import OpenSSH-format ECDSA keys; and its README examples accept any host key ([RSA.swift](https://github.com/orlandos-nl/Citadel/blob/main/Sources/Citadel/Algorithms/RSA.swift), [OpenSSH 8.8](https://www.openssh.com/txt/release-8.8), [Citadel #30](https://github.com/orlandos-nl/Citadel/issues/30), [Citadel #115](https://github.com/orlandos-nl/Citadel/issues/115), [Citadel](https://github.com/orlandos-nl/Citadel)). **Those gaps gate Tide's first real terminal session more than any engine choice does.**

### Three paths fit behind one seam

The options reduce to three, and a small protocol at the bytes-in, bytes-out, view and events boundary makes moving from the first to either of the others a swap rather than a rewrite.

| Path | What Tide builds | What Tide gets | Main risk | Use it for |
|---|---|---|---|---|
| A. SwiftTerm 1.99.x, then 2.0 | A version bump, Swift tools 6.2, Metal behind a setting, the resize path | VoiceOver, BiDi, Sixel, iTerm2 and Kitty images, thread-safe feeding | Open iOS input bugs; main-thread renderer cost | Shipping SSH sessions now |
| B. libghostty-vt with a Tide renderer | A `UIView` with renderer, text input, key mapping, selection, scrolling and VoiceOver: several thousand lines | An upstream-supported core, snapshots, tmux control mode, render holds, renderer threading under Tide's control | API churn until a tag; input and accessibility parity | A time-boxed spike, then adoption if the gate passes |
| C. Full libghostty via libghostty-spm | A wrapper around its UIKit terminal view, one or two days | Ghostty's Metal renderer, ligatures and font fallback | A 21-patch fork of an internal API that upstream dropped for iOS, kept largely by one maintainer | A quality yardstick, never the shipping engine |

Path A is cheap because Tide touches so little of SwiftTerm. Its call sites (`TerminalView(frame:)`, `feed(text:)`, `terminalDelegate`, `installColors`, the native foreground and background colors, `caretColor` and `font`) avoid everything 2.0 removes, namely `Terminal.parser`, `EscapeSequenceParser` and `getTerminal()`, and 2.0 makes `feed` "safe from another thread" and adds a `feedSender` handle for background transports ([MigratingFrom1To2.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/Sources/SwiftTerm/Documentation.docc/MigratingFrom1To2.md)). SwiftTerm's own SSH guide wires exactly what Tide needs: the delegate's `send` writes to the channel, channel data goes to `feed(byteArray:)`, and `sizeChanged` requests a PTY resize ([SSHIntegration.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/Sources/SwiftTerm/Documentation.docc/SSHIntegration.md)). The 1.99.1 manifest needs Swift tools 6.2 ([Package.swift](https://github.com/migueldeicaza/SwiftTerm/blob/v1.99.1/Package.swift)), which Tide's Xcode 26 requirement already covers ([Tide README](../../README.md)); compiling against 1.99.1 is the confirmation step.

Path B replaces `TerminalView` with a Tide-owned `UIView`, and its parts list is its cost: a Core Text renderer that draws dirty rows from the render-state iterators, later a Metal glyph atlas; `UITextInput` with marked text so IME, dictation and the software keyboard work, with the preedit overlay sized by `ghostty_unicode_grapheme_width`, which the header recommends for exactly that ([unicode.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/unicode.h)); `pressesBegan` and `UIKeyCommand` handling with a Tide-written table from `UIKey` HID usages to W3C codes; selection through libghostty-vt's gesture state machine, which must be called serially ([selection.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/selection.h)); copy and paste through the paste encoder; a scroll model using overscan rows; hyperlink taps from `ghostty_grid_ref_hyperlink_uri` ([grid_ref.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/grid_ref.h)); and VoiceOver. By this research's estimate, unvalidated, that is two to three weeks to "usable for vim and htop over SSH" and two to three months to parity with SwiftTerm on IME, selection, VoiceOver and hardware keyboards. Little can be reused. Upstream's 2,520-line AppKit surface view targets the full API and AppKit ([SurfaceView_AppKit.swift](https://github.com/ghostty-org/ghostty/blob/main/macos/Sources/Ghostty/Surface%20View/SurfaceView_AppKit.swift)), the deleted UIKit view had no input code, VVTerm's code is GPL-3.0 and cannot enter an MIT app, and libghostty-spm's MIT UIKit layer, written against the full API, is the best design reference. A hybrid that runs libghostty-vt inside SwiftTerm's renderer is not practical, because 2.0 deliberately hides SwiftTerm's `Terminal` and parser ([MigratingFrom1To2.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/Sources/SwiftTerm/Documentation.docc/MigratingFrom1To2.md)).

### Wire Citadel through the seam, never through SwiftTerm types

The seam belongs in the code before SSH lands, in an estimated two to four days of work: `TerminalSession` holds an engine behind a protocol, `TerminalHost` asks the engine for its view, and Citadel, `VirtualShell` and `LineEditor` talk only to the protocol. It is the same move that let Code App put Monaco and Runestone behind one editor interface ([Code App](https://github.com/thebaselab/codeapp), [Code App 1.8.0](https://github.com/thebaselab/codeapp/releases/tag/1.8.0)), and the same boundary Tide's design draws around its own editor engine ([Tide prior-art report](<iOS VS Code clone prior art.md>)). A sketch, with illustrative names:

```swift
@MainActor protocol TerminalEngine: AnyObject {
    var view: UIView { get }                                     // hosted by TerminalHost
    var events: AsyncStream<TerminalEvent> { get }               // title, pwd, bell, clipboard, links, notifications, prompt marks
    var onInput: (@Sendable ([UInt8]) -> Void)? { get set }      // keys, paste, mouse, query replies -> Citadel or LineEditor
    var onGridResize: ((TerminalGridSize) -> Void)? { get set }  // -> Citadel changeSize
    nonisolated func feed(_ bytes: [UInt8])                      // callable from the SSH event loop; the engine serializes
    func apply(theme: TerminalTheme, font: TerminalFont)
    func paste(_ text: String)
    func readText(_ scope: TerminalTextScope) -> String          // find in terminal, AI context
    func snapshot() -> Data?                                     // optional, for scene restoration
    func setVisible(_ visible: Bool)                             // stop rendering when hidden or backgrounded
}
```

Every member maps onto public API in both engines: SwiftTerm 2.0's thread-safe `feed`, delegate callbacks and copied reads, and libghostty-vt's `vt_write`, effects, encoders and formatter ([MigratingFrom1To2.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/Sources/SwiftTerm/Documentation.docc/MigratingFrom1To2.md), [vt.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt.h)). Several things stay outside it: Citadel's session lifecycle, the input accessory row (so it is identical across engines and shared with the editor's keyboard bar), the session list and the theme source. Tide's theme code already maps VS Code's `terminal.ansi*`, `terminal.background`, `terminal.foreground` and `terminalCursor.foreground` keys into SwiftTerm ([TerminalManager.swift](../../App/Sources/Model/TerminalManager.swift)), and libghostty-vt accepts the same values through its palette, foreground, background and cursor color options ([terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)).

Under Swift 6 the seam also absorbs a threading mismatch. Citadel delivers channel data on a SwiftNIO event loop while Tide's code is main-actor by default ([project.yml](../../project.yml)). SwiftTerm 2.0 tolerates feeding from that thread; libghostty-vt needs every call on a terminal serialized. The natural shape follows the header's own advice: one lock-protected owner for the non-`Sendable` handle, taken by the SSH read path for `vt_write` and by a `CADisplayLink` tick only for `begin_update`, with `end_update` and drawing done outside the lock ([render.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/render.h)). Three rules prevent subtle breakage. `WRITE_PTY` replies arrive synchronously inside `vt_write`, so they must be queued to the Citadel channel rather than written back re-entrantly ([terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)); dropping them would break programs that probe the terminal, such as vim, tmux and fish. Synchronized output needs the host's render-hold callback, because the render-state update "does not check for this" and a renderer that updates on every draw "will show half-drawn frames" ([render.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt/render.h)). And whichever engine runs, the grid-resize callback must reach Citadel's `changeSize`; with today's empty `sizeChanged`, remote programs would keep drawing at the size they saw first.

### The terminal renderer competes with the editor engine for the same hard parts

Path B's real price is that it asks Tide to build, for the terminal, the text-input machinery its design already commits it to building for the editor. Tide's editor today is a `UITextView` on TextKit 1 ([Tide README](../../README.md)), and its plan is to own a Core Text engine seeded from a Runestone fork because TextKit 2 fails at code-editor scale ([Tide prior-art report](<iOS VS Code clone prior art.md>)). Apple warns that a custom text view gives up "Text input, selection, accessibility, undo and redo, dictation, inline predictions, and more" ([WWDC26 session 370](https://developer.apple.com/videos/play/wwdc2026/370/)), and Runestone's source shows what recovering them costs, down to private API because "We can't make autocorrection work properly without using private API" ([TextInputView.swift](https://github.com/simonbs/Runestone/blob/main/Sources/Runestone/TextView/Core/TextInputView.swift)). A grid terminal needs less of that, with no autocorrection and simpler selection geometry, but the same marked-text handling, hardware-key mapping and VoiceOver support, and the same vulnerability to regressions in every iOS release. Both consequences follow. The work can be shared, as one module for font loading, glyph caching, Core Text shaping, key-code tables, marked-text overlays and the accessory row. And the risk compounds, because an IME or VoiceOver regression would then hit two custom surfaces at once. **The right rule is to build that substrate once.** If the spike's performance numbers clear the gate before the editor engine work begins, the terminal's input layer should be designed as the first client of a shared module; otherwise it should wait for the editor engine's input layer and inherit it. Either way the spike itself should run early, because it is cheap and produces the evidence the decision lacks, and until then SwiftTerm carries the terminal's input risk at no cost to Tide.

### Remote features favor libghostty-vt's extras, but SwiftTerm 2.0 covers the MVP

For the remote layer, libghostty-vt's extras line up with features Tide wants after 1.0 more than with its first release. Snapshots that restore parser state and stream older scrollback incrementally ([snapshot.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/snapshot.h)) suit an app that iOS suspends about five seconds after it leaves the foreground ([Apple](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)) and whose background activity Termius sees stop "usually within 20 to 30 seconds" ([Termius FAQ](https://docs.termius.com/help-center/faq/how-can-i-keep-termius-sessions-alive-in-the-background-on-ios-ipados.md)): a terminal could redraw instantly after the OS terminates Tide while `tmux new -A` reattaches the real session behind it, the reattach pattern Secure ShellFish ships ([HN](https://news.ycombinator.com/item?id=47065371)). tmux control mode in the VT core is the basis for mapping tmux windows to Tide terminal tabs, as Moshpit does ([build_info.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/build_info.h), [Moshpit](https://apps.apple.com/us/app/moshpit-terminal-for-agents/id6799896801)). OSC 133 prompt marks, OSC 7501 program status, notifications and progress effects ([terminal.h](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt/terminal.h)) serve agent supervision, signalling when a command or an agent CLI has finished and letting the user jump between prompts, and the formatter and search APIs ([vt.h](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/include/ghostty/vt.h)) supply terminal output as AI context and find-in-terminal. SwiftTerm 2.0 covers the first-release version of that list with copied reads such as `terminalContentSnapshot(region:)` and `getBufferAsData`, `observeOscEvents`, OSC 133 since 1.17 and OSC 7501 since 1.99.1 ([MigratingFrom1To2.md](https://github.com/migueldeicaza/SwiftTerm/blob/main/Sources/SwiftTerm/Documentation.docc/MigratingFrom1To2.md), [v1.17.0](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.17.0), [v1.99.1](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.99.1)). The differentiators, parser-complete snapshots and tmux control mode, are post-1.0 features, one more reason the switch can wait for evidence.

### App Store and license rules shape the packaging, not the choice

Apple's rules govern how libghostty-vt is packaged, not whether Tide can use it. A library compiled into the binary is not downloaded code, so Guideline 2.5.2 does not touch it ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Linking the static `.a` into the app binary is the lowest-risk path, since the encryption-segment problem upstream fixed concerned dynamic frameworks and the app binary is linked by Apple's toolchain; that reasoning is an inference, and so is the need for an `nm -u` audit of imported symbols in the spike, because upstream's CI checks exports, not imports. libghostty-spm's removal of a "private window blur API" ([libghostty-spm](https://github.com/Lakr233/libghostty-spm)) shows the full library has carried at least one such risk. A GPU renderer must also stop submitting work when its scene leaves the foreground, because Apple ties background GPU use to a dedicated entitlement for continued-processing tasks ([Apple](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)); the seam's `setVisible` exists for that. Neither libghostty-vt's iOS 13 minimum nor libghostty-spm's iOS 15 floor constrains Tide's iOS 17 target.

Licensing is compatible, with one trap. Ghostty's MIT license fits Tide's, and `NOTICE.md`, which already credits SwiftTerm, would add Ghostty plus the components vendored into the archive, simdutf, Highway, wuffs and compiler_rt, each checked against its license file in the pinned build ([NOTICE.md](../../NOTICE.md), [tip release](https://github.com/ghostty-org/ghostty/releases/tag/tip)). The trap is shell integration. Ghostty's bash script states that "Kitty is distributed under GPLv3, so this file is also distributed under GPLv3" ([ghostty.bash](https://github.com/ghostty-org/ghostty/blob/main/src/shell-integration/bash/ghostty.bash)), so Tide must never ship Ghostty's scripts and should write its own if it injects shell integration over SSH, as libghostty-spm did ([libghostty-spm](https://github.com/Lakr233/libghostty-spm)). VVTerm's GPL-3.0 code stays reference-only for the same reason, since the FSF holds that App Store terms "contradict the GPL's conditions" ([FSF](https://www.fsf.org/blogs/licensing/vlc-enforcement)).

In CI the prebuilt framework costs almost nothing. The `tip` URL is rebuilt nightly, so pinning means downloading one build, verifying its minisign signature, recording the Ghostty commit and re-hosting the file as a Tide release asset or vendored binary, wrapped in a local Swift package that XcodeGen consumes the way it already consumes `TideCore` ([tip release](https://github.com/ghostty-org/ghostty/releases/tag/tip), [project.yml](../../project.yml)). Two risks need checking in the spike. The simulator slice is arm64-only, so a CI build for `generic/platform=iOS Simulator` ([ci.yml](../../.github/workflows/ci.yml)) that also compiles x86_64 would fail to link and needs x86_64 excluded for the simulator SDK; and the slice's explicit `apple_a17` CPU model has to run on older Apple silicon Macs and on GitHub's runners ([GhosttyLibVt.zig](https://github.com/ghostty-org/ghostty/blob/48dde97e0413a27064e4c6182db3df6ee999db7d/src/build/GhosttyLibVt.zig#L125-L215)). Building from source instead would add Zig 0.17 to every macOS runner, plus Nix if Tide matched upstream's own build setup.

### Four conditions gate the switch

The plan that follows has four phases and a gate, and every duration in it is an estimate rather than a measurement. Phase 0, due before SSH lands, adds the seam, wraps SwiftTerm as the first engine, implements the resize path and records a replay corpus of raw SSH byte streams: vim editing and scrolling, `htop`, tmux with four panes, `cat` of a 50 MB log, `yes`, emoji, ZWJ, CJK, combining-mark and RTL test files, `kitty +kitten icat` and img2sixel output, and applications that use the Kitty keyboard protocol. Phase 1, about a week, moves SwiftTerm to 1.99.x with Metal behind a setting and records baselines on a 120 Hz iPad Pro and the oldest supported iPhone: frame-time p50, p95 and p99 and hitches over 16 ms from `os_signpost` and `CADisplayLink` timestamps, main-thread busy time, key-to-echo latency over LAN SSH, memory at 10,000 and 100,000 scrollback lines, and the IPA size delta. Phase 2, time-boxed to two or three weeks, builds a libghostty-vt engine with a whole-row Core Text renderer and basic input, runs the same corpus plus subsets of vttest and esctest, Unicode width cases, mouse modes and the Kitty keyboard protocol, and can wrap libghostty-spm's view for a day or two as a ceiling for how Ghostty rendering feels on iPad. Phase 3 is the gate, and every condition must hold.

| Gate condition | Suggested pass bar |
|---|---|
| Frame pacing | On device, p99 frame time and the count of hitches over 16 ms beat SwiftTerm 2.x with Metal by a clear margin, such as 30% fewer hitches, with no throughput regression |
| Input and accessibility parity | No regressions in Japanese, Chinese and Korean IME, dictation, the software keyboard with its accessory row, iPad hardware keyboards (Esc, Ctrl, Option as Meta, function keys, key repeat), selection and copy, or VoiceOver reading the visible screen |
| API stability | A tagged libghostty-vt release, or about three months without a breaking change in the functions Tide calls, with adapter upkeep of at most about a day per upgrade |
| Release hygiene | Complete license acknowledgements, and a TestFlight build that passes App Store processing |

If any condition fails, Tide stays on SwiftTerm 2.x and reopens the question when libghostty-vt is tagged, when upstream ships a GPU or Swift-view library, when upstream restores iOS builds and host-fed bytes to the full library, or when SwiftTerm's iOS fixes stall. If all four pass, Phase 4 moves the renderer to Metal, adds ligatures through Core Text shaping, Kitty graphics through an ImageIO decode callback, VoiceOver parity and snapshot-based scene restoration, and keeps SwiftTerm as a runtime fallback for at least one release, above all for right-to-left users, because SwiftTerm has BiDi and Ghostty does not.

## Conclusion

The useful shift in understanding is where libghostty's cost lives. The obstacle usually cited, a Zig toolchain and a self-maintained iOS build, turns out to be the cheapest part, removed by a signed nightly framework; the expensive part is IME, VoiceOver and hardware-keyboard quality on a second custom text surface. That makes the terminal decision a question of when Tide builds its own text-input substrate, which its editor roadmap requires anyway, rather than a terminal question at all. A seam turns the choice into an option whose value rises with time: each month of upstream work, from the render-state convergence to embedder-driven features to a 0.1.0 soname waiting for its tag, lowers the cost of exercising it, while the SwiftTerm 2.0 migration is a one-time cost Tide pays either way.

The schedule lesson points the other way. Citadel's RSA signing, keyboard-interactive authentication, ECDSA import and host-key verification gate the first real terminal session, and the engine decision can wait months behind the seam without delaying anything users see. When Tide does exercise the option, it will likely be the first iPad code editor on libghostty-vt, and therefore an unpaid iOS test lab for a library upstream verifies only by compiling, whose issue tracker is closed to outsiders and whose forge is about to move. Joining upstream's Discussions during the spike, with the replay corpus and on-device numbers in hand, is the cheapest way to make the first libghostty-vt tag fit an iPad embedder rather than adapting to one after the fact.
