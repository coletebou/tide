# Own the Editor, Run the Rest Remotely

No app on iPhone or iPad ships what a native Swift clone of VS Code would be: a native workbench and editor with language intelligence, VS Code's declarative ecosystem, Remote-SSH-style development and agent review in one open-source package. The roughly 25 prior attempts split three ways: native editors without a workbench (Textastic, Runestone, Buffer), web wrappers around Monaco or VS Code that inherit WebKit's input and process-lifetime problems (Code App's default mode, Blink Code, code-server in Safari), and 2026's AI remote controls (Cursor, Claude Code, Codex, Copilot) that review agent diffs but deliberately do not edit. Apple's rules, not engineering effort, fix the architecture: Guideline 2.5.2, the ban on spawning processes and the lack of in-process JIT together push compilers, language servers, code-running extensions and agent loops onto the user's own SSH host, so the device should own editing, the workbench and review while the remote machine owns execution. That sets the build-versus-buy line. Build the editor engine (TextKit 2 fails at code-editor scale and no maintained iOS library is ready, so Runestone's MIT source is a seed rather than a dependency), the workbench, a VS Code compatibility layer ported from MIT code, the remote session layer and the AI review loop; adopt SwiftTerm, Citadel on SwiftNIO SSH once its RSA, keyboard-interactive and key-import gaps are fixed, libgit2 or gitoxide, tree-sitter, a Swift LSP client and the MCP Swift SDK. From Termius-class clients, treat the now-free single-user feature set (host manager, Secure Enclave keys, jump hosts, port forwarding, snippets, a programmable keyboard row) as the floor, and copy Secure ShellFish's automatic tmux reattach rather than location-based keep-alive. From AI apps, copy Copilot-in-VS-Code's skeleton (side-bar chat, Cmd+I inline edits with Keep/Undo, a harness picker), Claude's diff comments sent back to the agent, Cursor's checkpoints and plan mode, Grok Bot's expiring Allow once / Always allow / Deny approvals and ChatGPT's cross-host task list, and keep all of it opt-in and consented, because forced AI produced Termius's worst 2026 reviews and Guideline 5.1.2(i) requires permission before personal data reaches a third-party model.

## About 25 iOS code editors exist, and none is a native VS Code

The iPhone and iPad market holds **about 25 established code editors, IDEs and developer tools, fewer than half still under active development**. Koder, Kodex, iVim, Pythonista and Pyto have gone dormant, Panic discontinued its Code Editor in 2021, and no editor launched in 2024–2026 has reached 100 US ratings. Rating volume still sits with old apps: **Koder keeps 12,133 ratings after four and a half years without an update**, against 3,788 for Working Copy, 2,553 for Textastic and 2,087 for Runestone ([Koder](https://apps.apple.com/us/app/koder-code-editor/id1447489375), [Working Copy](https://apps.apple.com/us/app/git-client-working-copy/id896694807), [Textastic](https://apps.apple.com/us/app/textastic-code-editor/id1049254261), [Runestone](https://apps.apple.com/us/app/runestone-text-editor/id1548193893)). Most of these apps are one developer's work, and they go dormant when that developer moves on, which makes a contributor model as much an architectural decision for an open-source clone as any library choice.

The survivors split into two families, and each achieved what the other could not. **Native editing surfaces** (Runestone, Textastic, Kodex, Buffer, Working Copy) deliver system-quality selection, Files integration, offline use, multiple windows and small downloads, but none documents a command palette, split editor groups or language servers. **Web editing surfaces** (Code App's default Monaco mode, Blink Code, CodeMan, and vscode.dev, code-server or Codespaces in Safari) deliver near-complete VS Code features cheaply and inherit WebKit's problems. vscode.dev cannot open local folders on iPadOS ("Local File System Access is Unsupported") ([vscode#146356](https://github.com/microsoft/vscode/issues/146356)), and code-server's own iPad guide warns that the keyboard sometimes disappears, that `cmd+n` opens a new browser window, that the Magic Keyboard lacks an Escape key, and that iOS memory management drops the app's state ([code-server iPad guide](https://coder.com/docs/code-server/ipad)). A cluster of wrapper apps exists only to patch those failures, and it has not won users: CodeMan, which advertises Command-key passthrough for VS Code servers, has 7 ratings ([CodeMan](https://apps.apple.com/us/app/codeman-vscode/id6759809062)).

The most telling data point comes from **Code App** (MIT, about 4,000 stars), the leading open-source VS Code-alike. It imitates the workbench in SwiftUI around Monaco in a web view, and in 2024 it added a native Runestone mode, "an editor with native text selection controls" ([Code App 1.8.0](https://github.com/thebaselab/codeapp/releases/tag/1.8.0)). Its Python and Java language servers, added later that year, run only in Monaco mode: `MainApp.swift` guards language-service startup with `!runeStoneEditorEnabled` ([MainApp.swift](https://github.com/thebaselab/codeapp/blob/main/CodeApp/Managers/MainApp.swift), [Code App 1.10.0](https://github.com/thebaselab/codeapp/releases/tag/1.10.0)). Users wanted native text handling badly enough for the maintainer to build a second editor, and the project could not bring its language features along. Code App's editor seam, an `EditorImplementationDelegate` that lets Monaco and Runestone sit behind one interface, is the abstraction a native clone should keep. Its bundled Node.js, Python, Clang-to-WebAssembly, PHP and Java runtimes, which make it a **962 MB download against Textastic's 26 MB**, are the cost a native clone should avoid ([Code App lookup](https://itunes.apple.com/lookup?id=1512938504), [Textastic lookup](https://itunes.apple.com/lookup?id=1049254261)).

Panic's 2021 post-mortem for Code Editor explains why the professional end of this market keeps failing. The app did not "generate enough revenue to cover its continued development", and Panic named the platform as the deeper problem: "The biggest technical hurdle is the inability to run external processes on iOS and iPadOS", apps "must use Apple's Javascript interpreter, JavaScriptCore", and "We wouldn't know if our approaches would be allowed on the App Store until we'd fully built and submitted them for review" ([Panic](https://panic.com/blog/the-future-of-code-editor/)). Panic also rejected the smaller product, a streamlined editor on File Provider, because it "didn't fully address the needs of modern web developers, plus we'd be facing stiff competition", which is roughly what Runestone and Textastic are today. In 2024 a Hacker News thread still called the iPad "the worlds most expensive thin client connected to a real computer somewhere else" ([HN](https://news.ycombinator.com/item?id=41448412)). Those blockers still hold in October 2026, so the opening is not another text editor but the workbench, remote development and VS Code compatibility together.

The momentum has moved to AI agent clients, and they embrace the thin-client reading instead of fighting it. Cursor for iOS entered public beta on June 29, 2026 to "launch and manage always-on agents from anywhere" ([Cursor changelog](https://cursor.com/changelog/ios-mobile-app)). OpenAI put Codex in the ChatGPT mobile app in May 2026 and reports that "More than 4 million people now use Codex every week" ([OpenAI](https://openai.com/index/work-with-codex-from-anywhere/)). The Claude app "is a client for Claude Code sessions rather than a place where code runs" ([Claude Code docs](https://code.claude.com/docs/en/mobile)), GitHub's Copilot coding agent reached GitHub Mobile in 2025 ([GitHub changelog](https://github.blog/changelog/2025-06-03-github-copilot-coding-agent-now-available-on-github-mobile/)), and the open-source Happy client has **24,240 stars** ([Happy](https://github.com/slopus/happy)). All of them show diffs, logs and approvals, and none edits. Cursor states that its app "is built for directing and reviewing agents, not for editing" ([Cursor help](https://cursor.com/help/ai-features/mobile-app)), and a Cursor reviewer complains that "any time an approval is needed it's on my laptop instead of letting me approve on my phone" ([Cursor reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=6767085653/sortby=mostrecent/json)). That is the gap: open the agent's branch over SSH, review it in a real diff editor, fix it by hand and approve its next command, on iPad and iPhone.

App Store reviews define what such an app must not do. In about 2,280 sampled reviews across 23 apps, pricing design draws the most complaints. Textastic's lifetime rating is 4.69, but its recent sample averages **3.51** after a move to a free download with a hard paywall ("I have to pay just to look at text content?"), and Blink's trial, which "requires you to sign up for an auto-renewing subscription", is called "a predatory dark pattern" ([Textastic reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1049254261/sortby=mostrecent/json), [Blink reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1594898306/sortby=mostrecent/json)). Stability comes next ("When I pull IT LOST ALL 4 HOURS OF WORK CHANGES", wrote a Buffer user), then non-native selection, lost keyboard focus and missing Escape keys ([Buffer reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=502633252/sortby=mostrecent/json)). Praise goes to apps that feel native and price fairly. A Runestone reviewer says "there is nothing between you and the code", and the pay-once models users accept carry the highest ratings: Working Copy at 4.85, Runestone's $9.99 Premium at 4.73 and Secure ShellFish's lifetime Pro at 4.82 ([Runestone reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1548193893/sortby=mostrecent/json), [runestone.app](https://runestone.app/), [Secure ShellFish](https://apps.apple.com/us/app/ssh-client-secure-shellfish/id1336634154)). Every iOS release breaks someone, too: a Runestone user reports the app "will not start" on iPadOS 26.6, and a Swift Playground user reports that on iPadOS 27.0.1 "every app I create, no matter how simple, crashes" ([Runestone reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1548193893/sortby=mostrecent/json), [Swift Playground reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=908519492/sortby=mostrecent/json)).

## Apple's Guideline 2.5.2, not engineering, decides where code runs

App Review Guideline 2.5.2 says apps may not "download, install, or execute code which introduces or changes features or functionality of the app", with a narrow exception for educational apps whose code stays "completely viewable and editable by the user" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). The developer agreement allows downloaded interpreted code only if it does not change the app's primary purpose, bypass OS security or "create a store or storefront", and hedges its learning-environment carve-out with conditions such as executable code taking over no more than 80 percent of the screen, so a professional IDE should not lean on it ([DPLA 3.3.1(B)](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/)). The technical floor is just as hard. `system()` is "unavailable: not available on iOS", so ios_system loads each command as an in-process framework ([ios_system](https://github.com/holzschu/ios_system)); embedded CPython has "no ability to use separate executables such as python or pip" ([Python docs](https://docs.python.org/3/library/intro.html)); and, per secondary sources, in-process JavaScriptCore runs without JIT while WKWebView's out-of-process web content gets it ([HN](https://news.ycombinator.com/item?id=40726948)). **On-device execution is limited to interpreters compiled into the binary** (WasmKit, a pure-Swift MIT interpreter for iOS 18+; embedded CPython; Lua) and to JavaScript and WebAssembly inside a WKWebView, which is how a-Shell runs clang-compiled Wasm ([WasmKit](https://github.com/swiftwasm/WasmKit), [a-Shell](https://github.com/holzschu/a-shell)). Native JIT, spawned processes and downloaded binaries are dead ends.

Enforcement shows where the line sits. In 2020 Apple threatened to remove iSH because it "is not self-contained and has remote package updating functionality", asked it to drop wget and curl, and then accepted its appeal ([iSH blog](https://ish.app/blog/app-store-removal)). In March 2026 Apple blocked updates to the vibe-coding apps Replit and Vibecode; MacRumors reported that Apple seems to object to showing generated apps "within the original app using an embedded web view" and "expects approval" if they open in an external browser instead ([MacRumors](https://www.macrumors.com/2026/03/18/apple-blocks-updates-for-vibe-coding-apps/)), and 9to5Mac reported the removal of a third app, Anything, under 2.5.2 and DPLA 3.3.1(B) ([9to5Mac](https://9to5mac.com/2026/03/30/apple-steps-up-crackdown-on-vibe-coding-apps-pulls-anything-from-the-app-store/)). **An AI agent that writes an app and previews it inside the IDE is exactly that pattern.** The defensible design keeps AI output as editable source that the user explicitly runs on their own host, with Safari as the preview fallback. No source shows how App Review treats an editor that executes commands only on a user-supplied SSH host; 2.5.2 governs code executed in the app, so remote execution looks safe, but that remains unverified.

Three more guidelines shape the product. Guideline 4.7 now permits "plug-ins" that are not embedded in the binary, with duties attached: filtering and reporting, per-instance consent before sharing data, an index with universal links, age gating, and, under 4.7.2, no exposing "native platform APIs or technologies to the software without prior permission from Apple". That makes a local extension host with native bridges a review risk. Guideline 4.2.7(e) says "Thin clients for cloud-based apps are not appropriate for the App Store", so a code-server wrapper can be one mode but never the whole app, and Guideline 5.1.2(i) requires apps to "clearly disclose where personal data will be shared with third parties, including with third-party AI, and obtain explicit permission before doing so" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Two licenses close off Microsoft's infrastructure. Marketplace offerings "are intended for use only with Visual Studio Products and Services", which is why code-server uses Open VSX ([code-server FAQ](https://github.com/coder/code-server/blob/main/docs/FAQ.md)), and the VS Code Server behind Remote Tunnels may not be used "if you do not have a license for Microsoft Visual Studio Code" ([VS Code Server license](https://code.visualstudio.com/license/server)).

Background execution is close to absent. An app has **about five seconds** after entering the background before suspension, extendable briefly with `beginBackgroundTask` ([Apple](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)), and Termius observes background activity stopping "usually within 20 to 30 seconds" ([Termius FAQ](https://docs.termius.com/help-center/faq/how-can-i-keep-termius-sessions-alive-in-the-background-on-ios-ipados.md)). iOS 26's `BGContinuedProcessingTask` lets a user-started job continue with progress in a system Live Activity, but the system "prioritizes the termination of tasks that reflect minimal or no progress" ([Apple](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)), and Apple's examples are media exports, so its acceptance for git clones or SFTP transfers is unverified. Guideline 2.5.4 limits background modes to their intended purposes, yet Termius, Secure ShellFish and Blink all keep SSH sockets alive through location updates ([ShellFish](https://secureshellfish.app/help/agentic-coding), [Blink](https://docs.blink.sh/advanced/advanced-ssh)), and Live Activities cannot help because they "can't access the network" ([Apple](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)). Memory is capped per device at unpublished limits, and the increased-memory-limit entitlement is "only available on some device models" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit)), so piece-table buffers, memory-mapped reads and checks of `os_proc_available_memory` before loading large files or local models are design inputs, not late optimizations.

The window and input shell changed twice in two years. iPadOS 26 gave every app resizable windows and a menu bar ("Going forward, every app on iPad is getting its own menu bar"), built through `UIMainMenuSystem` and `UIMenuBuilder`, and apps with storyboard menus no longer launch ([WWDC25 208](https://developer.apple.com/videos/play/wwdc2025/208/), [WWDC25 243](https://developer.apple.com/videos/play/wwdc2025/243/)). Building with the iOS 27 SDK makes the UIScene lifecycle mandatory ("Without it, your application will no longer launch"), makes iPhone apps fully resizable, and declares the idiom trait "no longer meaningful for any kind of layout decision" ([WWDC26 278](https://developer.apple.com/videos/play/wwdc2026/278/)), and the iPhone Duo foldable gives apps its full inner display only when they are built with the iOS 27.1 SDK ([Apple](https://developer.apple.com/iphone-duo/prepare/)). The practical shape is one window scene per workspace, layout by available width, every command in the main menu with a `UIKeyCommand`, and a Command Palette as the guaranteed entry point, since Apple Support says the menu bar appears only when Windowed Apps or Stage Manager is on ([Apple Support](https://support.apple.com/guide/ipad/use-the-menu-bar-ipadb4ede9db/ipados)). `wantsPriorityOverSystemBehavior` lets editor shortcuts run before text input ([Apple](https://developer.apple.com/documentation/uikit/uikeycommand/wantspriorityoversystembehavior)), but Cmd-Tab and Cmd-Space stay system-owned and the Magic Keyboard for iPad Pro has no Escape key ([MacRumors](https://www.macrumors.com/how-to/remap-modifier-keys-ipad-keyboard/)), so the keymap needs Escape alternatives and touch paths for F2, F8 and F12. An iOS 17 floor maximizes reach, but `UIMainMenuSystem`, per-command repeat behavior, `BGContinuedProcessingTask` and SpeechAnalyzer are all iOS 26.0 or later, so **an iOS 26 floor for 1.0 removes a whole layer of availability branches** ([UIMainMenuSystem](https://developer.apple.com/documentation/uikit/uimainmenusystem), [SpeechAnalyzer](https://developer.apple.com/documentation/speech/speechanalyzer)).

Licensing narrows the dependency list for an MIT app. GPL code cannot go in without putting the shipped app under GPL terms, and the FSF has argued that App Store terms "contradict the GPL's conditions" ([FSF](https://www.fsf.org/blogs/licensing/vlc-enforcement)); that rules out STTextView's GPLv3 option, Blink, iSH, VVTerm and Mosh. libgit2's GPLv2 carries a linking exception that permits distributing linked combinations "without any restriction coming from the use of this file" ([libgit2 COPYING](https://github.com/libgit2/libgit2/blob/main/COPYING)). VS Code itself (Code - OSS), Monaco and vscode-textmate are MIT, so algorithms and theme files can be ported with the copyright notice kept, and codicons are CC BY 4.0 ([VS Code license](https://github.com/microsoft/vscode/blob/1.142.0/LICENSE.txt), [codicons license](https://github.com/microsoft/vscode-codicons/blob/main/LICENSE)). The brand guidelines restrict using "Visual Studio Code or VS Code" on "your website, product, service", so the name belongs only in factual compatibility statements ([VS Code brand guidelines](https://code.visualstudio.com/brand)).

## TextKit 2 fails code editors, so the engine must be owned

Only three maintained libraries ship an iOS code-editing surface, and none is ready to depend on. **Runestone** (MIT, a custom Core Text engine, iOS-only) is the only one with production users, Xogot and Code App, but it is in maintenance mode: four default-branch commits since June 2024 and open crash reports, including a Writing Tools crash on iOS 26.1 and a red-black-tree out-of-bounds crash when text is replaced mid-highlight ([Runestone commits](https://github.com/simonbs/Runestone/commits/main), [#413](https://github.com/simonbs/Runestone/issues/413), [#424](https://github.com/simonbs/Runestone/issues/424)). Even Xogot had to fork it to highlight the executing line ([Xogot](https://blog.xogot.com/xogot-code-editing/)). **STTextView** is the most feature-rich but is GPLv3 or commercial, and its multi-cursor and find bar exist only on the AppKit side ([STTextView license](https://github.com/krzyzanowskim/STTextView/blob/main/LICENSE.md), [source tree](https://github.com/krzyzanowskim/STTextView/tree/main/Sources)). **CodeEditorView** (Apache-2.0) describes itself as "pre-release quality", and turning off wrapping "doesn't work properly on iOS" ([CodeEditorView](https://github.com/mchakravarty/CodeEditorView), [#90](https://github.com/mchakravarty/CodeEditorView/issues/90)). CodeEdit's fast MIT Core Text engine targets macOS 13 only ([CodeEditTextView](https://github.com/CodeEditApp/CodeEditTextView)), and in August 2026 the ChimeHQ text components (Neon, TextFormation, TextStory) passed to new individual maintainers, so they should be pinned by commit or vendored ([Massicotte](https://www.massicotte.org/blog/looking-for-maintainers/)).

Apple's own text views do not close the gap. UITextView has defaulted to TextKit 2 since iOS 16, and TextKit 2 estimates document height outside the viewport, behavior an Apple forum reply calls "correct and as-designed" ([Apple forums](https://developer.apple.com/forums/thread/761364?answerId=799739022#799739022)). In practice that means scroller jumps and, in Feedback FB15241823, a tap after a fast scroll that puts the caret "often dozens of paragraphs below", reproduced on iOS 17 through 18.1 ([textkit2-issue](https://github.com/nathantesler/textkit2-issue)). STTextView's author, four years into TextKit 2, wrote in August 2026 "I'm so tired of TextKit 2. this is dead end" ([Tsai roundup](https://mjtsai.com/blog/2025/08/15/textkit-2-the-promised-land/)), and Neon's author has found no way to do flicker-free per-keystroke highlighting on it ([Neon](https://github.com/slsrepo/Neon)). WWDC26 added public UITextView viewport hooks for line numbers and collapsible paragraphs, but only from iOS 27 and with nothing for multiple cursors ([WWDC26 370](https://developer.apple.com/videos/play/wwdc2026/370/)). TextKit 1 scrolls large documents more smoothly in one report ([Apple forums](https://developer.apple.com/forums/thread/729491)) and gives IME, dictation, accessibility and find for free, but iOS lacks its temporary attributes ([Apple](https://developer.apple.com/documentation/appkit/nslayoutmanager/addtemporaryattribute(_:value:forcharacterrange:))), so highlighting means mutating the text storage, and it has no multi-selection model. **VS Code-class features (minimap, scrollbar decorations, sticky scroll, go-to-line in a 200,000-line file) need an exact, cheap line-to-y mapping that TextKit 2's estimation fights.**

The alternative is expensive, and Apple says so: a custom text view gives up "Text input, selection, accessibility, undo and redo, dictation, inline predictions, and more", and "building a production-quality text editing experience from scratch is a lot of work" ([WWDC26 370](https://developer.apple.com/videos/play/wwdc2026/370/)). Runestone shows the price. Even with system selection UI from `UITextInteraction`, it calls private API through obfuscated key-value-coding strings because "We can't make autocorrection work properly without using private API", carries Korean and Chinese marked-text workarounds that "Even the Swift Playgrounds app does not get ... right for all languages in all cases", and was crashed by iOS 26.1's Writing Tools calling `text(in:)` out of range ([TextInputView.swift](https://github.com/simonbs/Runestone/blob/main/Sources/Runestone/TextView/Core/TextInputView.swift), [#413](https://github.com/simonbs/Runestone/issues/413)). Inferred from the history of these projects, **a ground-up engine at Runestone parity costs roughly 12–24 engineer-months**, and extending a Runestone fork with VS Code features (decorations, folding, minimap, multiple cursors, a large-file mode) roughly 6–12. The risk concentrates in IME, system services that call back into `UITextInput`, VoiceOver, and per-release regressions that no unit test catches.

The decision follows: own the engine, start from the cheapest seed, and draw the boundary first. An app-owned editor-engine interface (a versioned edit buffer, a line index, a selection set that is multi-range from day one, a decoration API for squiggles, find matches, bracket boxes, indent guides and gutter markers, and a layered token provider) lets the surface change without touching the workbench, the same seam that let Code App swap Monaco for Runestone. Tide's editor today, per its README, is a `UITextView` on TextKit 1 with a layout manager that draws decorations ([Tide README](../../README.md)). That is the right prototype and the wrong endgame: multiple cursors, folding and 200,000-line files are where TextKit 1 stops, and moving to TextKit 2 trades those limits for worse ones. The endgame is a Core Text engine with an AvalonEdit-style line tree for exact y-positions; a piece table or rope for large files, since VS Code's piece tree keeps memory "very close to the original file size" ([VS Code blog](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation)); engine-owned selections that report one primary range to `UITextInput` and draw the rest, with ChimeHQ's [IBeam](https://github.com/ChimeHQ/IBeam) as the design reference; folding as hidden lines in the tree; and a minimap drawn from cached token runs. Runestone's MIT source (line tree, per-line Core Text rendering, `UITextInteraction` and `UIFindInteraction` integration, years of IME fixes) is the fastest route there if forked and vendored. The fork should isolate its private-API paths, set code-editor input traits (autocorrection off, `inlinePredictionType = .no`, `writingToolsBehavior = .none`) ([Apple](https://developer.apple.com/documentation/uikit/uitextinputtraits/writingtoolsbehavior)), and run against a corpus of 50,000- and 200,000-line files, 200,000-character minified lines, CJK, emoji, RTL and CRLF on real devices with hardware keyboards, Pencil and VoiceOver.

### Highlight with TextMate grammars, structure with tree-sitter

VS Code tokenizes line by line and stores each line's end state, so after an edit it re-tokenizes only "until an equal end state is encountered", and it packs tokens as integer pairs so that a theme change needs a new color table rather than a re-parse ([VS Code blog](https://code.visualstudio.com/blogs/2017/02/08/syntax-highlighting-optimizations)). Pairing that model with **TextMate grammars** gives the ecosystem-compatible base: the same grammar and theme files VS Code uses, exact theme import, near-zero binary cost per language, and grammars that plausibly count as data rather than code under 2.5.2, an untested inference. The catch is the regex engine, since TextMate grammars need Oniguruma semantics. shiki-swift, created in August 2026, is a native Swift port of Shiki with Oniguruma, 242 languages and claimed byte-for-byte parity with Shiki 4.4.3, but it has 12 stars, "does not provide progressive tokenization or incremental editing", and self-reports about 131–136 ms to highlight a 256 KB JSON file on Apple silicon ([shiki-swift](https://github.com/fayazara/shiki-swift)). Porting vscode-textmate's MIT rule-matching semantics directly is the alternative ([vscode-textmate](https://github.com/microsoft/vscode-textmate/blob/main/src/theme.ts)). Fast pattern-based lexers remain valuable as the "guaranteed low-latency" first pass in Neon's three-phase model ([Neon](https://github.com/slsrepo/Neon)), but they cannot consume the long tail of grammars published on Open VSX.

Tree-sitter adds what regex grammars cannot: real syntax trees for folding, indentation, bracket structure, selection expansion and outlines. It costs binary size and flexibility, because every grammar is compiled C that cannot be downloaded at runtime. Generated `parser.c` files run from 0.02 MB for JSON to **30.53 MB for C#** (C++ 24.65 MB, Swift 22.05 MB), and CodeEdit's 38-grammar bundle ships as a 32.79 MiB zipped XCFramework ([tree-sitter-c-sharp](https://github.com/tree-sitter/tree-sitter-c-sharp), [CodeEditLanguages](https://github.com/CodeEditApp/CodeEditLanguages)). It also carries an ABI trap: Runestone pins tree-sitter 0.20.9 (language ABI 14) while current grammars such as tree-sitter-python declare ABI 15, and adding Runestone beside SwiftTreeSitter produces "196 duplicate symbols" ([Runestone Package.swift](https://github.com/simonbs/Runestone/blob/main/Package.swift), [#294](https://github.com/simonbs/Runestone/issues/294)). The sound plan is layered: a fast fallback, TextMate for coverage, tree-sitter compiled in for a curated set of top languages on a single ABI-15 runtime (swift-tree-sitter), and LSP semantic tokens on top whenever a remote server is connected. With tree-sitter, captures must map to synthetic TextMate scopes so that VS Code themes still apply; VS Code's own semantic-token fallback table is the starting map, and about 30–40 mappings cover the main categories, with small color differences in embedded-language corners ([tokenClassificationRegistry.ts](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/platform/theme/common/tokenClassificationRegistry.ts#L545-L582)).

### Port VS Code's declarative layer instead of reinventing it

Because Code - OSS is MIT, the fastest route to fidelity is porting, with notice, the parts users notice. VS Code ships two different fuzzy scorers, `fuzzyScore` in filters.ts (a banded dynamic program with camelCase and separator bonuses) and `scoreFuzzy` in fuzzyScorer.ts (which powers file picking), while its command palette uses word and substring matching with a 50-entry recently-used list. Each should be ported faithfully and run over UTF-16 code units to match JavaScript semantics, because substituting one matcher for another changes result order in ways users notice ([filters.ts](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/base/common/filters.ts), [fuzzyScorer.ts](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/base/common/fuzzyScorer.ts), [commandsQuickAccess.ts](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/platform/quickinput/browser/commandsQuickAccess.ts#L53-L56)). The default themes are now **Dark 2026 and Light 2026**, inheriting through Dark Modern and Dark+ to the Visual Studio base, and built-in theme files such as dark_plus.json contain JSONC comments that break strict JSON parsers ([workbenchThemeService.ts](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/workbench/services/themes/common/workbenchThemeService.ts#L42-L56), [dark_plus.json](https://github.com/microsoft/vscode/blob/1.142.0/extensions/theme-defaults/themes/dark_plus.json)). Color-registry defaults should be stored as expressions (`tab.activeBackground` derives from `editor.background`) rather than flattened hex, or imported themes that override a base key render wrong. Settings should layer built-in defaults, user `settings.json` and workspace `.vscode/settings.json` with language-specific blocks, and the keybinding service should evaluate two-stroke chords and when-clauses and register each binding as a `UIKeyCommand` ([default keybindings](https://code.visualstudio.com/docs/reference/default-keybindings)). For the look, the classic metrics (35 px tabs, a 48 px activity bar, a 22 px status bar) are the stable target for v1: VS Code 1.142 enables its floating-card "Modern UI" by default but under experiment control, so desktop users see either ([workbench.contribution.ts](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/workbench/browser/workbench.contribution.ts#L838-L842)). Workspace search cannot spawn ripgrep the way VS Code does, so it must run in-process, honoring `.gitignore`, `files.exclude` and `search.exclude` with VS Code's 20,000-result cap ([search.ts](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/workbench/services/search/common/search.ts#L32)), or as `rg` on the SSH host when the workspace is remote. On iPhone the desktop geometry does not fit a 390-point screen, so parts collapse into a navigation stack around a full-screen editor, and the iPhone Duo's inner display behaves like a compact iPad.

## Termius made the full SSH client free, which sets the remote baseline

### Adopt the host manager, keychain and keyboard, and skip the team features

Termius (iOS 8.0.3, October 14, 2026; **4.7 stars from 19,480 US ratings**) is the most complete mobile SSH client, and since September 30, 2026 almost every connectivity feature in it is free ([Termius lookup](https://itunes.apple.com/lookup?id=549039908&country=us), [Termius changelog](https://docs.termius.com/changelog/ios.md)). The free Starter tier covers SSH, SFTP, Mosh, Telnet and serial; local, remote and dynamic port forwarding; agent forwarding, jump-host chains and SOCKS or HTTP proxies; certificates, FIDO2 and Secure Enclave "biometric" keys; group-inherited host settings; snippets with multi-host execution; and shell-integrated autocomplete. Pro, at $15 a month or $119 a year in the App Store, sells only sync, startup snippets, session logs and cloud-inventory imports ([Termius pricing](https://termius.com/pricing), [App Store](https://apps.apple.com/us/app/id549039908)). For an open-source IDE, that makes the single-user connectivity set the expected baseline rather than a premium tier. Termius's sync design (SRP6a login, Argon2id key derivation, libsodium end-to-end encryption) is the reference if a custom sync backend is ever needed, although iCloud Keychain plus CloudKit, the Secure ShellFish and VVTerm model, avoids running one ([Termius encryption](https://docs.termius.com/security/encryption-overview.md), [VVTerm](https://github.com/vivy-company/vvterm)).

Most of Termius's 2025–2026 iOS work serves people supervising coding agents from a phone, the same people an iPad IDE targets. It added a Shift+Tab key "enabling actions for Claude Code and other AI tools", a speech-to-text input field for CLI agents, agents that start automatically on connect, image paste that uploads the file over SFTP to `/tmp` and inserts its path, OSC 52 clipboard support and a hide-keyboard key ([Termius changelog](https://docs.termius.com/changelog/ios.md)). Its own agent guide combines a local port forward to preview a dev server ("Hot reload still works"), `tmux attach` as a startup command, and `cd ~/my-project/src && claude` ([Termius blog](https://termius.com/blog/8-tips-for-using-ai-agents-on-mobile-in-termius)). One mechanism deserves reuse well beyond autocomplete: Termius "opens additional `exec` channels next to the main `shell` channel" to fetch paths and history, which works when servers allow `MaxSessions` of 2 or more ([Termius autocomplete](https://docs.termius.com/terminal/autocomplete-and-shell-integration.md)). The same trick can carry remote search, file listing and git status on a single connection.

The reviews show what to avoid and what wins. In 500 recent Termius reviews, the 66 that mention AI average **2.9 stars** ("can't dismiss the AI window … I have to quit the app completely"), account and login complaints average 2.3, and background disconnects, poor tmux scrolling and SFTP transfers with "zero progress feedback for a 10 gig transfer" follow ([Termius reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=549039908/sortby=mostrecent/json)). Secure ShellFish, built on SwiftTerm, has the field's best sentiment, **353 reviews averaging 4.80**, with its 93 file-related mentions averaging 4.7, because it exposes servers in the Files app and runs `tmux attach` automatically after iOS suspends it ([ShellFish reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1336634154/sortby=mostrecent/json), [ShellFish Files help](https://secureshellfish.app/help/files-app), [HN](https://news.ycombinator.com/item?id=47065371)). Developers also say outright that they want the editor and the SSH client merged. One described using "VS Code for writing configs/scripts, and a completely separate tool (like MobaXterm, SecureCRT, or Termius) for handling SSH jumps, serial console connections, and port forwards. The constant context switching was driving me crazy" ([HN](https://news.ycombinator.com/item?id=47180159)). The table maps Termius's patterns onto a VS Code-style IDE.

### Citadel carries the MVP only after four fixes

For the terminal, **SwiftTerm** (MIT, 1,738 stars) is the default. It powers Secure ShellFish and La Terminal, ships a UIKit view, an accessory row with Esc, Tab, Ctrl and arrows, OSC 52 and OSC 8, image protocols and an optional Metal renderer, and its 1.99.1 release on October 21, 2026 adds iOS pointer mouse reporting for tmux and vim ([SwiftTerm](https://github.com/migueldeicaza/SwiftTerm), [v1.99.1](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.99.1)). **libghostty** is the credible challenger: Termius 8.0.3 moved its renderer to it, as did Echo and VVTerm, but Ghostty's XCFramework build step has no iOS target upstream, so adopting it means maintaining a Zig build ([Termius changelog](https://docs.termius.com/changelog/ios.md), [GhosttyXCFramework.zig](https://github.com/ghostty-org/ghostty/blob/main/src/build/GhosttyXCFramework.zig)). No benchmark compares the two on iPad, so SwiftTerm now and a measured re-evaluation later is the right order. Emulation correctness matters more than the choice; Blink's reviews punish "corrupted screens even in simple stuff like top" and "control-c kills the entire connection" ([Blink reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1594898306/sortby=mostrecent/json)).

For SSH, most shipping iOS apps sit on C libraries (libssh2 under VVTerm, Moshi and Code App; libssh under Blink), because those cover legacy algorithms ([VVTerm](https://github.com/vivy-company/vvterm), [Blink SSHClient.swift](https://github.com/blinksh/blink/blob/raw/SSH/SSHClient.swift)). The pure-Swift option is **Citadel** (MIT) on SwiftNIO SSH, which already provides PTY sessions with window resizing, exec streams, jump hosts, reconnect modes, local and remote forwarding and an SFTP client ([Citadel](https://github.com/orlandos-nl/Citadel)). It has four gaps that block a 1.0. It signs RSA user authentication only as SHA-1 `ssh-rsa`, which **OpenSSH 8.8 disables by default** ([RSA.swift](https://github.com/orlandos-nl/Citadel/blob/main/Sources/Citadel/Algorithms/RSA.swift), [OpenSSH 8.8](https://www.openssh.com/txt/release-8.8)); it lacks keyboard-interactive authentication, which 2FA and PAM prompts need ([Citadel#30](https://github.com/orlandos-nl/Citadel/issues/30)); it cannot import OpenSSH-format ECDSA keys ([Citadel#115](https://github.com/orlandos-nl/Citadel/issues/115)); and its README examples validate host keys with `.acceptAnything()`, leaving known-hosts handling to the app. Agent forwarding is also out of reach without fork work, because SwiftNIO SSH supports exactly three channel types ([swift-nio-ssh](https://github.com/apple/swift-nio-ssh)). Worse for security maintenance, since April 2, 2026 Citadel has depended on a zero-star third-party fork of swift-nio-ssh pinned to 0.3.x instead of Apple's 0.15.0 ([Citadel Package.swift](https://github.com/orlandos-nl/Citadel/blob/main/Package.swift)).

The decision is to adopt Citadel but vendor it: implement RFC 8332 `rsa-sha2-256`/`rsa-sha2-512` signing, keyboard-interactive authentication and ECDSA import before 1.0, write a real known-hosts validator with fingerprints and changed-key warnings, default new keys to Ed25519, ECDSA or Secure Enclave P-256 with a Termius-style "Export to host" flow, and keep libssh2 (BSD-3) as a fallback transport only if RSA or legacy hosts prove common. Secure Enclave keys carry one hard UX consequence. The enclave "Works only with NIST P-256 elliptic curve keys" and "Can't encode preexisting keys", so those keys can be neither imported nor synced, and the key UI has to manage one per device ([Apple](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave)).

Background disconnects are the field's top reliability complaint, and users already accept the server-side fix. The robust design runs a per-host `tmux new -A -s <name>` on connect, reconnects and reattaches the moment the app returns to the foreground, restores scrollback, uses `beginBackgroundTask` only to close cleanly, reserves `BGContinuedProcessingTask` for user-started transfers and clones, and delivers "job finished" alerts through OSC 777 or a host-side hook instead of a resident socket, the patterns ShellFish and Moshi ship ([ShellFish terminal help](https://secureshellfish.app/help/terminal), [Moshi](https://getmoshi.app/pricing)). Location keep-alive, if offered at all, belongs off by default. Mosh, the classic mobile-resilience transport, is GPL-3.0 ([mosh COPYING](https://github.com/mobile-shell/mosh/blob/master/COPYING)), so an MIT app cannot embed it; Termius instead "uses its own library for Mosh compatibility" ([Termius](https://docs.termius.com/organize-and-connect-to-hosts/connecting-to-a-server.md)), and Eternal Terminal (Apache-2.0) is the licensable alternative ([Eternal Terminal](https://github.com/MisterTea/EternalTerminal)). Port forwarding for previews needs two iOS cautions: local ports must avoid Apple's reserved list, and forwarding stops when the app goes to the background ([Termius forwarding](https://docs.termius.com/organize-and-connect-to-hosts/port-forwarding-and-tunneling.md)).

### Files, git, language servers and extensions ride the same connection

Local folders work well on iOS once the rules are followed. `UIDocumentPickerViewController(forOpeningContentTypes: [.folder])` returns a security-scoped URL with recursive access that persists as bookmark data, with I/O wrapped in `NSFileCoordinator` ([Apple](https://developer.apple.com/documentation/uikit/providing-access-to-directories)). Change detection is the weak spot: iOS has no FSEvents, and `NSFilePresenter` hears only coordinated writes and can deadlock other processes if left registered while the app is in the background ([NSFilePresenter](https://developer.apple.com/documentation/foundation/nsfilepresenter), [FSEvents](https://developer.apple.com/documentation/coreservices/file_system_events)). A workable design layers a presenter on the workspace root that unregisters on background, file-descriptor watches only for open files, and a cheap metadata rescan on foreground and before git status, and it checks iCloud download status so a search does not trigger mass downloads.

For remote work, **no surveyed app offers a native equivalent of VS Code's Remote-SSH**. Blink hands off to vscode.dev or code-server, Code App edits over SFTP, and ShellFish hands editing to other apps through its File Provider ([Blink Code](https://docs.blink.sh/advanced/code), [Code App SFTP provider](https://github.com/thebaselab/codeapp/blob/main/CodeApp/Managers/FileSystem/SFTP/SFTPFileSystemProvider.swift)). The pragmatic MVP is a "Remote-SSH lite": an SFTP-backed workspace behind the same file-system protocol as local folders, conservative saves that check modification time and size before writing, and search, git and test commands sent through exec channels. A small headless companion agent on the remote host, multiplexing file watching, indexing, language servers and terminals over SSH, is the natural next step and avoids both VS Code Server's license and its undocumented protocol. It is a design inference, though: no surveyed app ships one in native Swift, and Moshi's optional host helper is the nearest precedent ([Moshi](https://getmoshi.app)).

For git, the pragmatic engine is **libgit2** (v1.9.7, August 2026), whose linking exception makes an unmodified, linked copy workable. Its Swift wrappers are stale (SwiftGit2's last release was in 2019), so a self-built XCFramework with TLS and libssh2 is the realistic packaging ([libgit2](https://github.com/libgit2/libgit2), [SwiftGit2](https://github.com/SwiftGit2/SwiftGit2)). **gitoxide** (Apache-2.0 per GitHub, 12,037 stars) is the modern alternative and already ships inside a-Shell ([gitoxide](https://github.com/GitoxideLabs/gitoxide)); no mature pure-Swift git exists. A Swift read path for refs, the v2–v4 index, loose objects and packs with delta resolution gives explorer decorations, gutter diffs and the Source Control view low latency for about a month of work by the research's estimate, while smart-HTTP push, merge and rebase stay with libgit2 or gitoxide. Two traps await that reader: index v4 prefix-compresses paths ([git index format](https://git-scm.com/docs/index-format)), and Apple's `Compression` "zlib" is raw DEFLATE, so git's zlib header and Adler-32 trailer must be handled separately ([Apple](https://developer.apple.com/documentation/compression/algorithm/zlib)). For remote workspaces, git simply runs on the host. Trust is the real requirement: Buffer's data-loss reviews and a Code App review saying it "doesn't revert changes in Git" show what users punish ([Code App reviews](https://itunes.apple.com/us/rss/customerreviews/page=1/id=1512938504/sortby=mostrecent/json)), and Working Copy's model of owning repositories and serving them to other apps through Files is the one to interoperate with ([Working Copy](https://workingcopy.app/)).

Language intelligence follows the same split. Process-based servers such as SourceKit-LSP, clangd and tsserver cannot run on iOS, so semantic features come from servers on the SSH host, speaking LSP over an exec channel's stdio through ChimeHQ's BSD-licensed LanguageServerProtocol and LanguageClient packages. Their `DataChannel` abstraction accepts a custom transport, with the warning that "its really important to ensure that all data passes in both directions, including the LSP-specific framing information" ([LanguageClient](https://github.com/ChimeHQ/LanguageClient)). Local syntax features (highlighting, folding, outline, breadcrumbs, bracket matching, a word index, fuzzy symbol search) must work offline with no server at all. Code App's limits are the cautionary example: LSP only in its web-editor mode, and for two languages ([Code App 1.10.0](https://github.com/thebaselab/codeapp/releases/tag/1.10.0)).

Extensions should arrive in tiers, and most of the value comes from the first. VS Code extensions are a `package.json` of declarative contribution points plus optional code ([contribution points](https://code.visualstudio.com/api/references/contribution-points)). Grammars, themes, snippets, language configuration and icon themes need no runtime and can be installed from Open VSX by downloading the `.vsix` zip, verifying its SHA-256 and loading its `contributes` block; the registry's leading Python extension alone shows **61 million downloads** ([Open VSX API](https://open-vsx.org/v3/api-docs), [Open VSX search](https://open-vsx.org/api/-/search?query=python&size=2)). Code-executing extensions belong on the remote host. A local web-extension host in a hidden WKWebView is technically possible, since web extensions run in a worker with "the full VS Code API" but no Node.js ([web extensions guide](https://code.visualstudio.com/api/extension-guides/web-extensions)), but the API surface is enormous, bridging native file or terminal access runs into Guideline 4.7.2, and an in-app gallery risks the DPLA's storefront clause. Tide's published roadmap lists "Open VSX web extensions" ([Tide README](../../README.md)); this research supports starting that item with declarative contributions and keeping code execution remote.

## Every AI vendor ships an iPad remote control, and none ships an editor

### Six products, six patterns worth copying

OpenAI and Anthropic converged on the same mobile shape: the phone steers agents that run elsewhere. Codex in the ChatGPT app starts, continues, approves and reviews tasks on Codex Cloud or on a paired Mac, Windows or SSH host, showing approvals, terminal output, diffs and test results, and remote access went generally available with one-to-one QR pairing on June 25, 2026 ([ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes), [Codex on mobile](https://learn.chatgpt.com/docs/mobile)). On desktop, ChatGPT Voice can start Codex tasks, check on them and switch between them by voice ([ChatGPT Voice](https://learn.chatgpt.com/docs/features/voice)), and OpenAI retired Canvas from its current models on May 28, 2026 in favor of writing and code blocks inside responses, a sign that agentic task review now outranks side-by-side documents ([ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)). The Claude app's Code tab drives cloud sessions, Remote Control of a session on the user's computer, and Dispatch to the desktop app. Cloud sessions show a diff badge such as "+42 -18", let the user comment inline on lines and send the comments with the next message, and can subscribe to a pull request to push fixes for CI failures and review comments ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)). Permission modes are visible on the phone (Accept edits, Plan, Auto, plus Manual for Remote Control), and Bypass is never offered from the app ([Claude Code on mobile](https://code.claude.com/docs/en/mobile)). Third parties cannot plug into either loop directly: Claude's cloud sessions and Remote Control require a claude.ai login rather than an API key ([Remote Control](https://code.claude.com/docs/en/remote-control)), and the research found no published API for driving Codex Cloud tasks.

Cursor is the clearest proof of iPad demand and of the gap. Its iPad app (July 2026) pins agent chats in a sidebar, places a review split beside the chat, shows full-width diffs, accepts Apple Pencil markup on screenshots and tracks up to **eight agents in Live Activities** ([Cursor on iPad](https://cursor.com/changelog/ipad), [Cursor for iOS](https://cursor.com/docs/cloud-agent/mobile)), yet it has no editor, terminal or file browser. Its desktop agent supplies the interaction patterns: automatic checkpoints before significant changes, stored locally apart from git; queued messages and "steer" at the next tool call; a Plan Mode on Shift+Tab that writes an editable markdown plan; and run modes (Auto-review, Allowlist, Run Everything) over a sandbox that blocks network access by default ([Agent](https://cursor.com/docs/agent/overview), [Plan Mode](https://cursor.com/docs/agent/plan-mode), [run modes](https://cursor.com/docs/agent/security/run-modes)). One trust lesson travels too: Cursor's mobile app requires leaving "Privacy Mode (Legacy)" irreversibly, which drew a 249-point "Tell HN" complaint ([HN](https://news.ycombinator.com/item?id=48737226)). GitHub Copilot in VS Code is the template for where everything sits: a Chat view in the Secondary Side Bar with a sessions list and four input controls (session target, agent, language model, permissions); inline chat on Cmd+I with an inline diff and Keep/Undo; ghost text plus Next Edit Suggestions marked by a gutter arrow; pending agent edits kept or undone one at a time; "Submit Feedback" on a commented range; and a harness abstraction hosting Copilot, a local agent, Claude and Codex side by side ([Chat view](https://code.visualstudio.com/docs/agents/run/chat-view), [inline chat](https://code.visualstudio.com/docs/chat/inline-chat), [reviewing edits](https://code.visualstudio.com/docs/agents/run/review-code-edits), [harnesses](https://code.visualstudio.com/docs/agents/run/agent-harnesses)). Copilot also stops automatic suggestions on metered connections, a courtesy a cellular iPad needs ([inline suggestions](https://code.visualstudio.com/docs/editing/ai-powered-suggestions)).

The Grok app adds little coding UX beyond voice with screen sharing and a system dictation shortcut ([Grok release notes](https://grok.com/release-notes)), but Grok Build, xAI's coding agent, runs as a TUI, headlessly or "through the Agent Client Protocol (ACP) in other apps", with Plan, Auto and Always-approve modes, and xAI's API is OpenAI-compatible ([Grok Build](https://docs.x.ai/build/overview), [modes](https://docs.x.ai/build/modes-and-commands), [Grok 4.7 API](https://docs.x.ai/developers/grok-4-7)). **Grok Bot**, launched August 11, 2026 on Cursor's platform (SpaceX had agreed in June to buy Cursor's maker, Anysphere, for $60 billion in stock), contributes the most complete approval model in the set ([Cursor docs](https://cursor.com/docs/grok-bot), [CNBC](https://www.cnbc.com/2026/06/16/spacex-spcx-cursor-acquisition-ipo.html)). Named Bots carry durable rules in their descriptions ("Never send external messages without approval"), share one persistent cloud computer, and hand work to each other visibly in group chats. Actions are gated by Allow once, Always allow (which saves a matching rule) or Deny, with a model-based Auto Review in which "Ask first" wins, and **approvals raised by unattended work expire after about ten minutes** ([Bots](https://docs.x.ai/grok-bot/bots), [approvals](https://docs.x.ai/grok-bot/approvals-security-and-privacy), [group chats](https://cursor.com/help/grok-bot/group-chats)). Secret requests are masked, kept out of the transcript and never shown to the model ([computer and apps](https://docs.x.ai/grok-bot/computer-and-apps)), and routine webhooks return 200 when a run starts, not when it finishes ([routines](https://cursor.com/help/grok-bot/routines)), a distinction any agent UI should surface.

| Copilot in VS Code | Desktop editor integration; cloud agent on GitHub Mobile | Side-bar chat with four pickers; Cmd+I Keep/Undo; Next Edit Suggestions; per-edit Keep/Undo and Submit Feedback; harness abstraction | The overall UI skeleton |

Sources: as cited in the three paragraphs above.

### Ship the edit-and-review loop before the agent cockpit

The terminal is the first agent feature. Claude Code, Codex and Grok Build all run as CLIs on an SSH host, so a terminal with Shift+Tab, Esc and Ctrl-C keys, voice input, image paste to `/tmp`, tmux reattach and finished-job notifications delivers agent supervision on day one, the bet Termius, Moshi and La Terminal made. The MVP proper is a VS Code-shaped loop that edits real files and runs commands over SSH. A chat panel in the secondary side bar carries a sessions list, streaming output and the four Copilot-style pickers, on bring-your-own-key providers (Anthropic Messages, OpenAI Responses, xAI's OpenAI-compatible endpoint, any OpenAI-compatible or Ollama server), with keys in the Keychain and an explicit consent screen before workspace content leaves the device. Context comes from `@` mentions for files, folders, the selection, open editors, terminal output, git diffs and problems, plus read, list and grep tools that let the model gather the rest; Cursor 2.0 removed most manual pickers because "Agent can now self-gather context" ([Cursor 2.0](https://cursor.com/changelog/2-0)). Inline edit on Cmd+I streams a diff into the buffer with Keep and Undo per hunk.

Agent mode, the in-app "Local" harness, edits through `str_replace`, create and patch tools, runs shell commands on the SSH host with output streamed into the terminal panel, checkpoints before each edit, offers a read-only Plan mode, and supports four permission levels (ask, allowlist with Always-allow rules, classifier review, run everything) with unattended approvals that expire. A multi-file review view lists changed files with +/− counts, shows inline or side-by-side diffs, accepts or rejects per hunk, and sends line comments back to the agent. The cheapest high-leverage item is rules compatibility: reading `AGENTS.md`, `CLAUDE.md` and `.claude/rules`, `.github/copilot-instructions.md`, `*.instructions.md` with `applyTo`, and `.cursor/rules/*.mdc` makes existing repositories work unchanged ([custom instructions](https://code.visualstudio.com/docs/agent-customization/custom-instructions), [Cursor rules](https://cursor.com/docs/rules)). Voice dictation through SpeechAnalyzer's `SpeechTranscriber`, falling back to `DictationTranscriber` biased with contextual strings drawn from workspace symbols, completes the touch input story ([SpeechTranscriber](https://developer.apple.com/documentation/speech/speechtranscriber), [DictationTranscriber](https://developer.apple.com/documentation/speech/dictationtranscriber)).

Structured harness support comes next. The Agent Client Protocol ("A protocol for connecting any editor to any agent", 4,473 stars) has adapters for the Claude Agent SDK and Codex, Grok Build speaks it natively, and the Cursor CLI documents it, though no official Swift SDK exists ([ACP](https://github.com/agentclientprotocol/agent-client-protocol), [claude-agent-acp](https://github.com/agentclientprotocol/claude-agent-acp)); Codex app-server offers JSON-RPC 2.0 over stdio as OpenAI's equivalent ([Codex app-server](https://learn.chatgpt.com/docs/app-server)). Running those agents on the SSH host and rendering their tool calls, approvals and diffs in the same review UI is how a third-party app reaches Claude Code and Codex without the first-party login. The later items rank behind that: MCP connectors; a cloud-agent inbox over Cursor's public Cloud Agents API, whose server-sent-event run streams expire with `410 stream_expired` ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)); Live Activities; AI review of local changes before commit; next-edit completions, for which the research found no public Cursor Tab or Copilot NES API and which Copilot keeps off bring-your-own-key models ([language models](https://code.visualstudio.com/docs/agent-customization/language-models)); memory; routines, which need a server because iOS has no reliable scheduler; live previews; and multi-agent orchestration.

### Keep the AI plumbing thin, provider-specific and consented

Neither Anthropic nor OpenAI ships an official Swift SDK ([Anthropic SDKs](https://platform.claude.com/docs/en/api/client-sdks)), and the APIs drift fast: within September 2026 OpenAI introduced GPT-6 Astra, brought GPT-6 Sol and Luna to Codex, and shipped GPT-6.1 Sol ([ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)), and GPT-6.1 Sol does not support the `none` and `minimal` reasoning efforts ([OpenAI](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra)). **Thin per-provider clients over URLSession server-sent events**, exposing each provider's specific features, make a safer core than a lowest-common-denominator abstraction, with Hugging Face's AnyLanguageModel or Apple's Foundation Models protocol reserved for on-device and Private Cloud Compute paths ([AnyLanguageModel](https://github.com/huggingface/AnyLanguageModel)). Edits should arrive through provider-native tools (Claude's text editor tool with `str_replace`, OpenAI's `apply_patch` operations) or plain function tools, normalized into one internal edit model that feeds one review UI ([text editor tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool), [apply_patch](https://developers.openai.com/api/docs/guides/tools-apply-patch)). Because `str_replace` needs unique, whitespace-exact matches, the applier needs fallbacks (re-read, fuzzy match, full-file rewrite) and conflict detection against the user's concurrent edits. Keys belong in the Keychain through the Security framework directly, since the popular wrappers have been inactive since mid-2024 ([KeychainAccess](https://github.com/kishikawakatsumi/KeychainAccess)).

MCP is worth supporting but is mid-transition. The official Swift SDK (1,512 stars) supports Streamable HTTP and OAuth 2.1 with PKCE and dynamic client registration, but its last release was 0.12.1 in May 2026 ([MCP Swift SDK](https://github.com/modelcontextprotocol/swift-sdk)), and the July 28, 2026 specification is a breaking revision that removes protocol sessions and the `initialize` handshake and deprecates dynamic client registration in favor of Client ID Metadata Documents, which need a hosted HTTPS metadata URL ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Only remote MCP servers are possible on device, since stdio servers are local processes, so stdio servers run on the SSH host, and provider-hosted MCP (Claude's MCP connector, OpenAI's and xAI's remote MCP tools) is the lighter first step because it needs only a URL and a token.

Bring-your-own-key is the default because every zero-key route has strings attached. Apple's on-device model has a **4,096-token context window per session** under iOS 26 and generates about 30 tokens a second at roughly 0.6 ms per prompt token on an iPhone 15 Pro, so a 1,500-token prefix costs about a second before the first token ([TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window), [Apple ML Research](https://machinelearning.apple.com/research/introducing-apple-foundation-models)): fine for commit messages, chat titles and summaries, too slow and too small for keystroke completion. Private Cloud Compute offers a 32,000-token reasoning model with "no cloud API costs to developers who have less than 2 million first time downloads", behind a managed entitlement and a per-person daily quota ([WWDC26 241](https://developer.apple.com/videos/play/wwdc2026/241/), [Private Cloud Compute](https://developer.apple.com/documentation/foundationmodels/adding-server-side-intelligence-with-private-cloud-compute)). Anthropic's Claude for Foundation Models package authenticates genuine app builds with App Attest, but usage bills the developer and it requires iOS 27 ([Claude for Foundation Models](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/apple-foundation-models)). Sign in with ChatGPT lets open-source apps spend a user's plan through a loopback-redirect OAuth flow that excludes hosted MCP, file search and other Responses features ([Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source), [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)), and xAI's Grok OAuth showed no public third-party client registration ([xAI](https://x.ai/news/grok-opencode)). The product tension is real; one Hacker News commenter put it as "Asking a user to create and enter their own API key is a bar too high for good UX" ([HN](https://news.ycombinator.com/item?id=48536776)).

Two rules govern how AI appears. Guideline 5.1.2(i) requires disclosure and explicit permission before personal data goes to third-party AI ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)), which in practice means consent before workspace content is sent to any model, and Termius's 2026 reviews show that AI a user cannot dismiss costs more goodwill than it earns, so every AI surface needs a persistent off switch and none should appear unbidden. Security deserves the same weight: keys and SSH keys in the Keychain, prompt injection treated as a live threat through repository files, MCP results and web content, and approvals for unattended runs that expire, as Grok Bot's do.

## The ledger: own five layers, adopt everything beneath them

The subsystem decisions reduce to one rule. Build the five layers where native quality and VS Code fidelity are the product (the workbench, the editor engine, the VS Code compatibility layer, the remote session layer and the AI review loop), and adopt permissively licensed, maintained components everywhere beneath them.

| Layer | Decision | Components and licenses | Main risk |
|---|---|---|---|
| Workbench shell | Own: build | SwiftUI parts, command registry, Quick Input, main menu; [Code App](https://github.com/thebaselab/codeapp) as a reference only | UIScene, menu-bar and iPhone resizing rules change yearly |
| Editor engine | Own: build from a seed | Fork and vendor [Runestone](https://github.com/simonbs/Runestone) (MIT); [IBeam](https://github.com/ChimeHQ/IBeam) (BSD-3) and [CodeEditTextView](https://github.com/CodeEditApp/CodeEditTextView) (MIT, macOS) as designs | IME, Writing Tools, VoiceOver and per-release regressions |
| VS Code compatibility | Own: port | Code - OSS (MIT) scorers, theme files, piece tree, bracket-pair tree; codicons (CC BY 4.0); Seti icons (MIT); Open VSX declarative packages | Trademark use; no Microsoft Marketplace |
| Remote session layer | Own: build on adopted SSH | Remote Explorer, known hosts, ssh_config import, SFTP workspace, tmux reattach, Ports panel, file change detection | Background suspension; servers with `MaxSessions` 1 |
| AI review loop | Own: build thin | Per-provider SSE clients, edit normalizer, diff review, permissions, rules loader | API drift; Guideline 5.1.2(i) consent |
| Terminal | Adopt | [SwiftTerm](https://github.com/migueldeicaza/SwiftTerm) (MIT); libghostty (MIT) after benchmarking | A Zig build if moving to libghostty |
| SSH protocol | Adopt, vendor, fix | [Citadel](https://github.com/orlandos-nl/Citadel) (MIT) on swift-nio-ssh (Apache-2.0); [libssh2](https://github.com/libssh2/libssh2) (BSD-3) fallback | Fork pin delays security fixes; RSA, 2FA, ECDSA gaps |
| Session persistence | Adopt host tools | tmux; [Eternal Terminal](https://github.com/MisterTea/EternalTerminal) (Apache-2.0) later | Mosh is GPL-3.0 |
| Parsing and highlighting | Adopt engines | [tree-sitter](https://github.com/tree-sitter/tree-sitter) (MIT), [swift-tree-sitter](https://github.com/tree-sitter/swift-tree-sitter) (BSD-3), a TextMate engine (vscode-textmate port or [shiki-swift](https://github.com/fayazara/shiki-swift), MIT) | Grammar binary size; one ABI-15 runtime |
| Git engine | Adopt plus a Swift read path | [libgit2](https://github.com/libgit2/libgit2) (GPLv2 with linking exception) or [gitoxide](https://github.com/GitoxideLabs/gitoxide) (Apache-2.0) | Stale wrappers; zlib framing; data loss |
| Language servers | Adopt protocol, run remotely | [LanguageServerProtocol and LanguageClient](https://github.com/ChimeHQ/LanguageClient) (BSD-3) over an SSH `DataChannel` | No on-device server processes |
| MCP | Adopt | [MCP Swift SDK](https://github.com/modelcontextprotocol/swift-sdk); provider-hosted MCP first | 2026-07-28 breaking revision; SDK lag |
| Agent harnesses | Adopt protocols on the host | [ACP](https://github.com/agentclientprotocol/agent-client-protocol) adapters, Codex app-server, agent CLIs in tmux | No official Swift ACP SDK |
| Apple frameworks | Adopt | SpeechAnalyzer, Foundation Models and Private Cloud Compute, Keychain and Secure Enclave, `BGContinuedProcessingTask` | iOS 26 floor; Secure Enclave is P-256 only |

Sequencing follows the dependencies. The engine boundary and the device test corpus come first, because every later editor change depends on them. The remote baseline (Remote Explorer, SSH terminal, keychain with known hosts, SFTP workspace, tmux reattach, local forwarding, remote language servers and git) comes next, because the agent's shell, the language servers and remote search all ride that connection. The edit-and-review AI loop builds on it, followed by the engine replacement (piece table, multiple cursors, folding, minimap, a large-file mode) and ACP harnesses; MCP, cloud-agent inboxes, a File Provider extension, sync, an Eternal Terminal or clean-room Mosh transport and tmux control mode can follow 1.0. The editor estimates behind this order (weeks for the boundary, one to three months to stand up a Runestone fork, three to nine months for VS Code features and core replacement) are inferences from comparable projects, not measurements.

Measured against this ledger, Tide's published architecture already sits on the recommended path in four places: a Foundation-only core package with fast host-side tests, a `WorkspaceFileSystem` protocol designed so a remote SFTP folder plugs into the same explorer and editors, a pure-Swift `.git` reader for branch, status and diffs, and SwiftTerm for the terminal, whose pinned 1.19.0 covers an MVP ([Tide README](../../README.md), [project.yml](../../project.yml)). Three decisions remain open: when to replace the TextKit 1 editor with an owned engine, whether to keep the iOS 17 floor or move to iOS 26, and how narrowly to scope extensions.

Several load-bearing questions remain unverified and deserve prototypes before commitments. No public benchmark compares TextKit 1, TextKit 2 and a custom engine on iOS at 50,000–200,000 lines. App Review's treatment of downloaded TextMate grammars, user-entered API keys, commands executed only on a user's SSH host, and `BGContinuedProcessingTask` for network work has not been tested. Whether Citadel's swift-nio-ssh fork accepts RFC 8332 algorithm names is unknown, SwiftTerm and libghostty have not been measured against each other on iPad, and the vendor documentation itself conflicts in places (Grok Bot's iPad support, and Cursor's description of Remote Control).

## Conclusion

The constraint and the market now point the same way. Apple forbids local execution, and in 2026 the AI vendors made remote execution the mainstream way to code from a phone, so the iPad's old "thin client" weakness has become the architecture the market chose. Once execution lives on a remote host, one SSH connection carries the terminal, files, search, git, language servers and the agent's shell, as Termius's exec-channel autocomplete already shows. That turns the least glamorous layer into the critical path: RSA SHA-2 signing, keyboard-interactive authentication, known-hosts verification and reconnect gate every headline feature, AI included, so Citadel's gaps are a schedule risk rather than a footnote.

The vendors' gap is structural rather than temporary. Each AI vendor's mobile app is bound to its own cloud and login, and Cursor's "not for editing" and Claude's claude.ai-only Remote Control are business choices, not missing features. An open-source native editor that edits, reviews and approves for any agent running on the user's own host occupies a position no vendor app is built to take. Owning that position means owning an editor engine and vendored forks of Runestone and Citadel, which raises the maintenance load at exactly the point where every predecessor died. An open contributor base, a device test matrix run against every iOS beta, and a free core that never paywalls viewing or editing are therefore architecture decisions in their own right, not project management.
